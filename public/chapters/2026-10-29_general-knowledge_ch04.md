# 第四章　版本與資料庫的不同時間：為何昨天的檔案未必救得回網站

一份文書可以開啟「歷程」，回到修改前的版本；一套網站也可以重新部署昨天的程式。兩者看起來都在「回到過去」，卻不是同一件事。網站可能有程式碼、資料庫、照片、登入權限與第三方服務，每項資料都可能有不同的時間線。若只把其中一條時間線倒回昨天，其他部分仍留在今天，系統未必能正常運作。本章要分清三種不同的歷史：**文件版本、程式版本與資料狀態**。

## 一、版本紀錄的首要價值是能說出「哪一版」

假設一份報名公告星期一修改價格、星期二改時間、星期三新增聯絡方式。若合作平台保留文件歷史，星期二的公告可以被找回。但你需要問：這份歷史只涵蓋文字嗎？外部圖片是否仍存在？當時公告連結指向哪個報名表單？文件歷程回答的是某項內容曾長什麼樣子，不自動保證相關服務也同時保持在同一時點。微軟 OneDrive 的版本歷史功能確實可選擇較早檔案版本，卻不等同復原整個業務流程。[R05]

程式碼版本管理提供另一種歷史。Git 的官方教材說明，追蹤中的檔案經過加入暫存與提交後，才會形成該次提交的快照；未被追蹤、未被加入的檔案不會自動進入歷史。[R07] 因此即使某個專案有 Git 倉庫，程式碼版本也不是電腦所有資料的備份。被忽略的密鑰、使用者上傳內容、執行時產生的報表或遠端資料庫，都可能根本不在倉庫裡。這不是 Git 壞掉，而是 Git 管的是一組指定內容的修訂歷史。

假設網站因新版程式出錯而退回舊版，這個動作可能救回正常按鈕；但若新版程式已把資料表改為新的欄位格式，舊版就未必能理解新資料。反過來，把資料庫回復到昨晚，程式碼仍是今天的版本，也可能出現欄位不存在或資料格式不符。版本管理讓程式可回頭比較和退回，卻沒有提供「整個世界一起倒轉」的能力。

## 二、資料庫為什麼不是放在資料夾裡的普通檔案

一份普通文字檔通常可以理解為某個時間點的完整內容。資料庫則必須在不同使用者同時讀寫時，維持多筆資料之間的關係與規則。假設報名一人需要同時建立「訂單」和「班次名額已減少」兩項變動；若只成功一項，可能造成超賣或無主訂單。資料庫使用交易等機制，是為了管理這類同時變動的狀態。備份時若在不適當的時刻只複製部分資料，便可能得到不能一致解釋的副本。

SQLite 的官方線上備份 API 文件指出，備份 API 可在資料庫正在使用時建立可用快照，並避免傳統檔案拷貝需要長時間鎖定或失敗時可能損毀的若干問題。[R08] 這不表示普通複製對任何資料庫都必然失敗；關鍵在於**複製是否遵守該資料庫的一致性規則**。對沒有專業背景的管理者而言，真正要問技術人員的不是「檔案有沒有複製」，而是「這份備份可否在獨立環境成功開啟、查詢及恢復我們最重要的一組關聯資料」。

更大型的資料庫也有不同策略。PostgreSQL 官方文件區分 SQL 匯出、檔案系統備份與連續封存三種主要方法，並明確說明各有取捨。[R09] SQL 匯出較容易理解：把資料庫內容轉成可在另一環境重建的邏輯資料；但它不會自動帶來每一秒的歷史。對高頻變動資料而言，某些部署會使用基本備份配合持續記錄變更的日誌，來達到指定時間點復原。PostgreSQL 的 WAL 連續封存文件說明可以在適當條件下回放日誌到指定位置，但也增加維護複雜度，且需要連續完整的日誌鏈。[R09]

這裡不需要把讀者訓練成資料庫管理員。理解三種方法的差異，就足以看懂「我們每天匯出資料庫」和「我們可以回到事故前幾分鐘」不是同一種承諾。前者有明確但稀疏的時間點；後者需要額外機制與可驗證的前提。向網站供應商詢問復原能力時，應要求說明**哪個時間點、涵蓋哪些資料、是否有演練過**，而不是只接受「我們有備份」的回答。

## 三、網站的照片可能不在資料庫裡

假設一個作品展示網站，作品表格記錄上傳者、作品編號、審核狀態與圖片位置；圖片本體存在另一個檔案服務。若資料庫復原到星期二，但圖片服務仍保持星期三狀態，可能出現資料表指向已不存在的圖片。相反地，若圖片回復到舊狀態、資料表卻較新，則可能產生沒有資料列對應的孤兒圖片。即使兩個系統都各自成功還原，**它們彼此不一致**仍可能讓網站失敗。

要處理這種問題，一種方法是設計跨服務的共同復原標記或清單，記下某次備份涵蓋的資料庫快照、附件集合、程式版本及必要設定；另一種方法是在恢復後對照資料關係，找出缺失並重新處理。哪種合適取決於產品與服務能力。一般使用者未必需要自己實作，但至少應把「照片在哪裡」「誰可以下載原始檔」「只還原資料表時會少掉什麼」列為方案驗收問題。NIST 的應變規劃重視系統資源的相依關係，這正是復原不能只看單一檔案的理由。[R10]

有些資料還帶有外部世界的不可逆結果。例如寄信、扣款或發出證書，即使把自己的資料庫回到發信前，也無法讓收件者忘記已收到的郵件。若系統已對外完成一筆付款，復原舊資料庫可能把付款狀態變回「未付」，卻不能自動從金流服務追回或取消已完成的交易。這類情況必須依賴對帳與補償流程，而不是認為備份能撤銷一切。這是從分散資料狀態推導的設計判斷，不是某個支付服務的實際測試。

## 四、資料歷史和真實性仍是兩件事

歷史版本能證明「這份檔案在某次紀錄裡是這樣」，但不能證明當時內容就是正確的。若工作人員早在星期一便把一個電話填錯，星期二、星期三、星期四都忠實保存它，還原到星期二仍然錯誤。對需要準確性的資料，還原後必須另外依據權威來源、原始單據或當事人確認。文件版本應被視為**內容狀態的證據**，不等於外部事實的真相。

此外，檔案可以算雜湊（例如 SHA-256）以檢查某份內容和先前記錄的位元是否一致。若雜湊不同，表示內容或位元序列發生變動；若一致，可以在所用演算法與紀錄可信的條件下，提高「同一份位元資料未改變」的信心。但它仍不能判斷業務內容是否正確，也不能代替備份副本。單獨存放在同一個可被修改位置的雜湊紀錄，對惡意篡改的防護也有限，因為攻擊者可能同時改內容和紀錄。這屬一般完整性原理，不能把通過雜湊檢查說成已通過所有安全稽核。[R14]

## 五、一個具體而完整的恢復判斷

假設一個小型網站昨天晚上八點開始使用新版本，今天上午發現部分報名顯示重複。管理員手上有昨天七點的資料庫匯出、昨天七點的程式提交與今天所有上傳照片。若直接把網站整套退回昨天七點，昨天晚上至今天上午新增的合法報名可能消失；若只退程式，新版已改過的資料仍可能留下。合理做法是先停止持續產生錯誤的入口，保留目前資料的唯讀副本和事故紀錄，找出受影響的資料列，再評估能否以小範圍修復，而不是無差別覆寫整庫。這是教學假設，沒有對真實服務執行修改。

這段推演也說明兩種能力的差異。**版本回退**是把某項內容換回先前已知版本；**業務復原**則是讓多個資料來源、規則與外部事件重新一致。前者可能是後者的一個動作，但絕非全部。對多服務網站而言，應事先確認主資料所在、相關附件、資料庫備份方式及對帳辦法；沒有這些準備，事故現場即使有十份 ZIP，也可能不知道先用哪一份。

## 六、不要讓「技術名詞」遮住可驗收的問題

當供應商說「我們有 Git」「有 SQL Dump」「有快照」「有 WAL」，這些都是有意義的機制名稱，但每一種保護不同狀態。值得追問的是：它能恢復哪種失誤？恢復點多密？是否包含必要附件、設定與權限？若還原單一部分會不會破壞其他部分？能否在不碰正式資料的情況下先驗證？

版本管理讓更動可比較，資料庫備份讓資料狀態可重建，跨服務對帳讓業務關係可重新成立。將它們分清，才不會把「有舊版本」誤當成「不會失去訂單」。這也是為什麼備份計畫必須從整個工作流程出發，而不能只從一個檔案副檔名開始。[R08][R09][R10]
