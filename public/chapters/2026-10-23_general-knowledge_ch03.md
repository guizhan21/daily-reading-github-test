# 第三章　小鎖頭能證明什麼：HTTPS、憑證與信任鏈

瀏覽器連上網站時出現安全警告，使用者往往直覺以為「網站被駭了」。反過來，看到網址列有鎖頭，就認為網站不可能是詐騙。這兩種推論都超過證據所能支持的範圍。HTTPS 要解決的是：連線雙方能否建立受到保護的傳輸通道，以及用戶端能否根據其信任設定驗證自己正在連向哪個名稱。它不負責保證網站經營者永遠誠實，也不負責判斷頁面上的促銷內容是真是假。[B10][B11]

## 一、HTTPS 不只是 HTTP 前面加一個字母

HTTP 描述請求與回覆如何交換；TLS 則在傳輸階段提供加密、完整性及身分驗證機制。以常見的 HTTPS 連線為例，瀏覽器先透過某種傳輸機制與服務建立通信路徑，再經 TLS 協商保護參數及金鑰，之後把 HTTP 訊息放在受保護通道中傳輸。使用 HTTP/3 時，TLS 1.3 的交握與 QUIC 結合，細節和傳統 TCP 承載方式不同，但其安全目標仍包括建立加密與驗證基礎。[B10]

先分清三個詞。**機密性**是讓沒有取得金鑰的第三方難以讀出通道內容；**完整性**是讓接收者能察覺資料是否在傳輸中被非法改動；**驗證**是在既定信任模型下確認對方能證明某個身分。三者相互配合卻不是同一件事。只有加密、沒有確認對方是誰，仍可能與冒充者建立一條加密通道；只有認得網站名稱、卻沒有防篡改能力，也不足以保護交易內容。

TLS 1.3 的標準將協定概括為交握階段與紀錄層。交握負責協商參數、建立共享密鑰材料並驗證身分；紀錄層以協商結果保護資料。這是解釋原理，不意味著每次載入網頁都使用全新、完整且相同的交握流程。連線恢復、協定協商與網路條件可能改變具體往返數；不應把某個示意流程當作所有瀏覽器封包的固定排序。[B10]

## 二、憑證是什麼，為何有「鏈」

公開網站使用的憑證通常涉及 X.509 公鑰基礎設施。網站提供的終端實體憑證會把某些識別資訊與公鑰連結起來；瀏覽器再驗證憑證的簽章、有效期、名稱適配及可以追溯到可信任信任錨的路徑。實務上會遇到中繼憑證與根憑證，合起來稱為憑證鏈。RFC 5280 規範憑證格式與路徑驗證的主要要求，並強調信任錨是驗證程序的輸入，屬於依賴端的信任決策。[B11]

把這想成一連串背書很容易理解，但比喻不能代替機制。某個中繼憑證的合法性，不是因為「它說自己被信任」，而是簽章與規則在用戶端信任路徑中獲得確認。即使憑證本身尚在日期範圍內，也可能因名稱不符、鏈缺失、演算法不被接受或本機時鐘嚴重錯誤而驗證失敗。反過來，憑證驗證成功也只能支持「這條通道到達了與驗證規則相符的名稱」，無法判定網站所售商品一定存在。

**域名控制驗證**與**企業身分背書**更應分開。像 Let's Encrypt 的自動化簽發流程會透過 HTTP-01 或 DNS-01 等挑戰，驗證申請方對特定名稱具有控制能力。HTTP-01 的典型做法是讓憑證機構從指定的網址路徑取得挑戰內容；DNS-01 則透過 DNS TXT 記錄證明控制。這些流程有助於自動簽發憑證，卻不是對網站商業倫理或內容可信度的全面審核。[B13]

## 三、瀏覽器如何知道連的是哪個名字

在共用主機和 CDN 環境，同一個對外位址可能提供多個網站。連線客戶端可以在 TLS 交握中透過伺服器名稱資訊協助服務端選擇適合的憑證；之後還須由客戶端依規則完成身分驗證。若站點部署時只設好 HTTP 路由，卻未為新增的自訂網域取得相容憑證，便可能出現「IP 可以訪問，網域顯示憑證錯誤」的情況。此時問題不是網頁 HTML 本身，而是加密握手與名稱驗證沒有正確配合。[B10][B11]

這也說明「直接打 IP 連 HTTPS」並不一定可靠。憑證往往是為域名簽發的，直接用 IP 連線時，若沒有相應的 IP 身分配置與伺服器支援，名稱比對便可能失敗。別人傳來一個數字 IP，聲稱它是「同一個網站的安全捷徑」，不能因它能回覆內容就假定安全。正確的網站識別應以你原本信任的網域與驗證機制為中心，而不是靠肉眼比對首頁長相。

## 四、HSTS 為何讓「改成 HTTP 試試」可能失敗

很多網站把 HTTP 入口重新導向 HTTPS，這只代表伺服器接到明文 HTTP 後要求改走安全連線。HSTS 的概念更進一步：網站可透過 `Strict-Transport-Security` 告訴支援的瀏覽器，未來一段時間對此主機應直接使用安全傳輸；瀏覽器也可能依預載清單持有規則。RFC 6797 描述這套政策的用戶端與伺服器互動。[B12]

因此，某個曾經啟用 HSTS 的網域即使憑證出了問題，也未必能簡單透過網址列改 `https` 成 `http` 來繞過。這本來是降低降級攻擊風險的設計，不是瀏覽器故意跟站長作對。如果管理者把 HSTS 保留時間設得很長，卻尚未確保所有相關主機都能穩定提供 HTTPS，可能為後續遷移或子網域調整製造麻煩。部署政策應當和憑證自動續期、名稱配置一起考慮。

這也關乎排障倫理：面對憑證錯誤，不應把「關閉安全檢查」當作優先修復方案。對一般使用者來說，警告本身可能是唯一阻止敏感資料流向錯誤端點的線索。站點管理者需要檢查憑證覆蓋範圍、簽發狀態、網域指向、鏈是否完整與裝置時間，而不是叫每個訪客忽略警告。

## 五、假設情境：剛綁定自訂網域卻顯示不安全

假設一個課程網站原先使用託管平台提供的子網域，現在加上自有域名。平台後台顯示部署已完成，但用自己的網域開啟會得到憑證錯誤。第一個問題應是該域名是否確實加進正確專案、DNS 指向是否符合平台要求、憑證簽發是否已完成。若平台使用 Let's Encrypt 自動簽發，還要檢查域名控制挑戰是否能正常通過。Vercel 的官方文件列出 DNS 設定、CAA 記錄、原有驗證記錄等可能阻礙憑證簽發的條件；但某項是否適用仍須看當時的平台提示，不能把可能清單當成已發現的根因。[B06][B13]

另一種情況是站點部分頁面顯示正常，某些圖片或腳本在瀏覽器被阻擋。這可能涉及 HTTPS 頁面載入不安全子資源的混合內容政策，並不等同主文檔憑證無效。修復方向是查清被阻擋的實際請求，以及是否能以安全來源提供；盲目重新簽發整站憑證未必有用。把錯誤落到具體資源、具體階段，是避免「看起來都叫 SSL 問題」的關鍵。

## 六、證書更新、失效與時間的現實

憑證有有效期，網站管理者不應依賴人工每隔很久才想起要續簽。自動化系統可以在域名控制驗證順利、平台設定正確的前提下完成更新；但這是「可自動化」，不是「永不會故障」。DNS 變更、授權限制、網路代理改寫驗證路徑或權限撤銷都可能使續期流程失敗。簽發機構文件會隨挑戰類型與政策更新，本書只說明截至查證日的制度與概念，不承諾每個服務商的固定週期或介面操作。[B13]

也要區分三個時鐘。憑證自身的有效期是其中之一；使用者裝置的系統時間影響對有效期的判斷；DNS 快取與 CDN 配置有各自更新時間。出現「新憑證已簽發，但部分人仍看到錯誤」時，可能涉及流量路徑或多台邊緣節點未一致配置，不能只盯著憑證檔案。反過來，如果單獨一台設備的時間嚴重偏離，也可能只有它出現驗證問題。這些是合理的診斷分支，不是對某個真實事故的結論。


## 補充：憑證錯誤不應靠修改使用者端安全設定處理

同一張錯誤頁上寫著「連線不安全」，可能包含截然不同的狀態：瀏覽器無法信任簽發鏈、憑證指定的名稱與目前網址不一致、有效期不符，或被政策要求只接受 HTTPS。這些錯誤的處理責任可能分布在域名管理者、託管平台、憑證簽發流程和用戶端。若只有某一台電腦遇到問題，應比較該裝置時間、瀏覽器更新狀態與其他設備結果；若所有設備都出錯，則優先調查站點實際提供的憑證及其對外路徑。與其叫使用者忽略警告，不如保留錯誤代碼與測試環境，讓站點管理員在服務端修正。

也要避免另一種宣傳誤解：保密連線並不代表你的 DNS 查詢或瀏覽行為對所有網路參與者都不可見。TLS 主要保護其承載的應用資料，沒有自動為每條名稱查詢提供相同保護。瀏覽隱私涉及更多網路與瀏覽器機制，不應從網址列的小鎖頭推導出超出協定範圍的保證。[B10][B11]

## 七、如何精確說明安全性，而不過度宣傳

更負責任的網站說明是：「我們使用 HTTPS 保護瀏覽器與網站之間的傳輸，並透過適當的身分驗證機制確認連線端點。」不應宣稱「有 HTTPS 就能確保所有資料永不外洩」。若網站後端資料庫權限過寬、管理者帳號被盜、伺服器日誌記錄敏感內容、使用者被誘導進入外觀相似的惡意域名，HTTPS 也不會直接解決這些問題。

本章材料以 TLS、PKI、HSTS 與憑證簽發機構的一手規範為核心，沒有評鑑任何個別站點的安全等級。安全是持續的系統性工作：要把運輸安全、程式權限、憑證管理、帳號保護和組織流程放在一起看。當瀏覽器的小鎖頭從「絕對安全」的象徵，還原成一個有明確條件的技術訊號，才有能力在真正的憑證錯誤面前做出不犧牲安全性的判斷。
