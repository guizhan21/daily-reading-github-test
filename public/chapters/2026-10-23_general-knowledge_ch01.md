# 第一章　網址不是地址：瀏覽器如何找到網站

一個網站在自己的電腦可以開啟，換到手機卻顯示找不到伺服器；把網域指向新主機後，有些人看見新版，有些人還在舊站。這類現象常被統稱為「網路不穩」，其實可能連網路傳輸都尚未開始。要理解網站，第一步不是認識伺服器，而是弄清楚瀏覽器把人類輸入的名稱轉成什麼。網路並不直接理解「我的報名網站」這個概念；它需要分辨一個資源的名稱、要連到哪個服務，以及後續向服務要求哪個頁面。[B01][B02]

## 一、網址表達的是資源，不等於機器所在地

以假想網址 `https://course.example.com:443/orders?id=42#detail` 為例，最左邊的 `https` 是方案，指出使用何種協定及安全連線語意；`course.example.com` 是主機名稱；`:443` 是埠，這裡明寫了 HTTPS 常用的預設埠；`/orders` 是路徑；`?id=42` 是查詢部分；`#detail` 是片段。RFC 3986 把這些組件放在同一個語法框架內，卻沒有說每個組件都由 DNS 管理。DNS 主要處理名稱對應的各式記錄；路徑與查詢字串通常交給之後的 HTTP 服務解讀；片段一般交由使用者代理程式在取得文件後處理，不會作為 HTTP 目標 URI 的片段傳給伺服器。[B01][B14]

這裡有一個重要區別：**域名不是 IP，IP 也不是完整網站**。一個域名可以回覆多個位址，供負載平衡或不同網路條件使用；多個網站也可以在同一個對外 IP 上，由連線時提供的主機名稱決定服務哪個站。若錯把域名與機器一對一綁死，便很難理解 CDN、託管平台與共用主機的運作。IP 位址可以是 IPv4，也可以是 IPv6；某些服務的解析結果可能隨位置、網路與時間而變。這些變化不一定代表錯誤。

再看 `course.example.com` 與 `example.com`：前者是子網域，後者是較上層名稱。把一個子網域設在平台上，不表示上層網域或其他子網域會自動跟著設定。當 `www` 能開、沒有 `www` 不能開，先查兩者記錄是否正確，而不是一律清除瀏覽器資料。**名稱相似不代表 DNS 設定相同**，這是部署網站時第一個值得反覆確認的事實。

## 二、DNS 查詢為什麼需要不只一台伺服器

DNS 是分散式、階層化的名稱系統。簡化地說，電腦先詢問可用的解析服務；若沒有可使用的快取，遞迴解析器可以逐層追問有權告知下一段名稱資訊的伺服器，最後取得權威來源的資料。這個設計避免每台電腦都保存全世界網站的位置，也讓不同組織能管理自己的名稱空間。所謂**遞迴解析器**，是代替用戶尋找答案的一方；所謂**權威名稱伺服器**，是在指定區域擁有原始記錄的一方。這兩者常被混淆，結果是把「換 DNS 伺服器」當作「修改網站 DNS 記錄」。前者改變查詢路徑，後者改變權威資料，並非同一操作。[B02][B03]

DNS 最常見的 A 記錄提供 IPv4 位址，AAAA 記錄提供 IPv6 位址；CNAME 讓一個名稱別名指向另一個名稱，並不是直接寫入網頁內容；MX 關係到郵件交換；TXT 可以承載各類文字型驗證資料。現代 DNS 還有 HTTPS／SVCB 記錄，能傳達服務端點與協定參數，提醒我們「DNS 永遠只有 A 記錄」也是過時印象。[B03][B05] 這些記錄服務不同目的，不應看到一個 A 記錄正確就推定所有功能都能正常運作。例如使用網站託管服務時，根網域與子網域可能要填不同類型的目標；具體值應以當時平台顯示的官方設定為準，不要照搬別人的 IP。

DNS 也不是域名註冊商的專屬功能。註冊商管理域名持有與委派的行政關係；實際 DNS 區域資料可以交由獨立供應商管理。對一個域名而言，若委派的名稱伺服器不是你以為的供應商，你在另一個控制台新增 A 記錄，外界仍可能完全看不到。這時即使那個控制台顯示「儲存成功」，也不能視為部署完成。真正有價值的問題是：目前對外公開的權威鏈指向誰、它提供什麼答案？

## 三、TTL 為什麼讓「剛改好」不等於「所有人立刻看到」

DNS 的 TTL 是記錄可在快取中保留的時間上限語意，以秒表示。假設某記錄原先 TTL 為 3,600 秒，一個解析器在變更前一分鐘剛把舊答案存下，它可能在剩下接近一小時內繼續回覆舊值；另一個解析器因快取剛過期，已取得新答案。這是依規範產生的合理差異，而不是「DNS 在全球依序搬運資料」的畫面。權威資料更新後，快取仍可在既定條件內返回先前的答案。[B02][B03]

這個例子是便於理解的**假設計算**，並非對任一實際 DNS 提供商的實測。3,600 秒等於 60 分鐘；但實際看見新記錄的時間會受查詢位置、遞迴解析器快取、用戶端快取、記錄種類及平台配置影響，不能用 TTL 單獨承諾全世界同步時間。若準備切換網域，可先降低舊記錄的 TTL，等待既有長 TTL 的快取逐步到期，再在變更窗口修改；等切換穩定後，依需要調整。降低 TTL 也不會把已經存於其他地方的舊答案即刻刪掉。

有時候你剛創建新的子網域，查詢者卻一直說不存在。原因不一定是記錄建立失敗；DNS 會對某些不存在的名稱或記錄類型回覆進行**負面快取**，減少重複詢問不存在資料的負擔。RFC 2308 專門說明這類否定答案的快取。這讓「我已經新增了名稱，為什麼舊網路還是回覆 NXDOMAIN」成為有機會由快取解釋的現象，但也不能因此忽略權威記錄仍未正確建立的可能。[B04]

## 四、DNS 的三種「正常但容易誤解」

第一種是同一個域名對不同查詢者回覆不同位址。許多大型服務刻意利用多位址、區域路由與負載平衡。若把其中任一個 IP 當成網站的永久地址，隨後把它寫死在程式或防火牆設定，就可能在供應商改動時失效。正確的判斷不是「查到不同 IP 一定出問題」，而是核對這些答案是否符合服務商正式公布的配置與預期範圍。

第二種是 DNS 查詢成功，網頁卻仍不能開啟。DNS 的回答表示取得某種名稱記錄，不表示該位址的網路路徑可達、目標埠有服務、TLS 憑證有效或 HTTP 應用程式正常。甚至 DNS 所指的伺服器可以準確地回覆一個 404。把整條連線想成接力賽，DNS 只交出第一棒所需的方向，而不是替所有參賽者保證完成。

第三種是「清掉快取」有時有效，有時無效。瀏覽器 DNS 快取、作業系統快取、路由設備及公共遞迴解析器各自有可管理的狀態；清除自己電腦的資料，不一定改變上游解析器仍保留的答案。Windows 的 `nslookup` 可以指定查詢的 DNS 伺服器，比較不同解析器的回覆，但不能把一次查詢結果當作整個世界的真相。[B21] 若同一個錯誤還涉及網站部署狀態，盲目反覆清快取可能浪費排查時間。

## 五、假設情境：報名站換到新平台

假設一個活動報名網站原先指向主機 A，現在改到託管平台 B。管理者在域名供應商修改記錄，但隔天有人看到新版，有人仍開舊站。可以先分別確認：官方平台要求填寫的 A 或 CNAME 是什麼？域名目前委派的權威名稱伺服器是誰？權威回覆是否已改？不同遞迴解析器回覆是否不同？舊記錄 TTL 多久？根網域與子網域是否各自配置？若權威還是舊值，應修改真正管理記錄的地方；若權威已新、部分快取仍舊，則以時間和查詢差異作證據，避免立刻重複修改造成更多混亂。Vercel 的官方排查文件同樣先要求確認域名已加到專案、記錄與平台給定值相符，再檢查名稱伺服器及當地快取。[B06]

這個案例不代表使用者目前任何站點真的發生上述故障。重點是把主觀描述「有些人進不去」拆成一組可以驗證的命題。人們常在事故中急著調整五項設定，卻沒有在每次調整前留下原值。等到網站恢復，反而無法辨認到底是哪一步有效。保持「改一項、量一次、記錄時間與查詢來源」的紀錄，是在分散式系統排錯中維持因果判斷的方法。

## 六、辨識邊界與更可靠的說法

有人會說：「域名能解析，就等於網站已上線。」不對。DNS 僅回覆資源記錄；應用服務可用性要再往下檢查。也有人說：「DNS 傳播一定要 48 小時。」這不準確。不同記錄、快取與名稱伺服器委派有不同收斂條件，部分平台文件可能給出較長的觀察窗口，但不是整個網際網路統一的秒表。[B02][B06] 還有人把瀏覽器網址列的路徑或片段誤當成 DNS 記錄；這會引導到錯誤設定頁面。

最後要承認本章的限制：RFC 描述協定機制，不保證每家 DNS 供應商如何配置快取、故障切換及特殊記錄。托管平台文件是當時的操作說明，可能在日後更新。若要判斷一個真實網站，仍須取得當時的實際 DNS 答覆與平台設定，而不是把教學中的假設值當作現場資料。理解名稱解析的目的，不是背一串記錄縮寫，而是在「找不到站點」時辨認你究竟有沒有走出第一道門。
