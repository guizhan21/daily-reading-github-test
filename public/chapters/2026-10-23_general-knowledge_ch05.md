# 第五章　同一個人，為什麼在不同網站不能互讀資料：CORS、Cookie 與瀏覽器邊界

前端網站與後端 API 各自在不同網域，明明兩邊都能打開，瀏覽器卻報「跨來源」錯誤。有人發現用命令列可以呼叫 API，放進網頁就失敗；有人用手機登入正常，在嵌入式頁面卻總是掉登入。這些現象常讓開發者把網路、安全與帳號系統混在一起。真正的核心，是瀏覽器不只是一個傳送 HTTP 的工具，它也為不同來源的網頁執行隔離政策。[B17][B18]

## 一、同源政策保護的是瀏覽器中的哪一條線

瀏覽器同源政策的基本比較單位是**方案、主機名稱與埠**。`https://a.example.com` 和 `https://b.example.com` 即使同屬一個組織，仍是不同來源；`http://a.example.com` 和 `https://a.example.com` 也不同；同一主機但不同埠，依這個標準同樣不同來源。這是讓一個網站載入的程式，不會理所當然讀取另一個網站或服務的私有資料的安全邊界。[B17]

設想瀏覽器正在一個網站登入信箱，同時你打開陌生宣傳頁。如果任何網站都能在背景直接讀取別的分頁回傳的私人信件，登入狀態就會成為重大風險。同源政策的目的，是防止一般網頁腳本隨便獲得其他來源的讀取權限。它不是說不同來源完全不能互動：圖片、腳本、導向、表單等操作有不同規則，而 `fetch` 和某些跨來源回應的讀取會受特別限制。把同源政策概括成「不同域名不能連線」是錯的。[B17]

這也解釋了一個常見現象：從自己的電腦用命令列發 API 請求成功，從瀏覽器執行的 JavaScript 卻報 CORS 錯誤。命令列程式不是被同一套瀏覽器同源政策約束的網頁腳本。這不代表 API 應被視為公開而安全，也不代表瀏覽器出錯；只是執行環境的信任與權限模型不同。若為了「讓前端能用」而把服務端授權全部關掉，將安全邊界拆除，可能造成真正的資料外洩。

## 二、CORS 是讓來源之間有條件分享讀取權

CORS 全名為 Cross-Origin Resource Sharing，主要透過 HTTP 標頭讓伺服器告知瀏覽器，哪些來源可以讀取特定跨來源回應。典型地，服務端可以回傳 `Access-Control-Allow-Origin` 指出獲准的來源；對於需要憑證的跨來源回應，則還涉及 `Access-Control-Allow-Credentials` 與用戶端的憑證傳送模式。CORS 的中心是瀏覽器讀取權限，不是使用者身分授權制度。[B18]

某些跨來源請求會先由瀏覽器發送 `OPTIONS` **預檢請求**，詢問伺服器是否允許接下來的方法和自訂標頭。對方回應符合要求後，瀏覽器才送出主要請求；但並非所有跨來源請求都會預檢，例如符合特定條件的簡單 GET 便可能直接送出。若伺服器只處理 POST，卻未妥善處理預檢 OPTIONS，就可能出現「後端路由明明存在，瀏覽器還沒真正 POST 就報錯」的情況。[B18]

必須分清：**預檢通過，不表示 API 的業務操作一定獲准**。伺服器仍須對實際請求進行認證、授權與輸入檢查。反過來，CORS 失敗也不能證明使用者密碼輸錯；瀏覽器腳本可能只是無權讀取回應。由於安全限制，JavaScript 通常拿不到 CORS 失敗的全部細節，開發者應到瀏覽器 Console 與 Network 查看實際問題。把「CORS error」拿去當登入失敗訊息，會導致錯誤的排查方向。

## 三、為什麼跨站帶 Cookie 不能簡單設星號

對不帶憑證的一些跨來源讀取，服務端可能使用萬用字元 `*` 作為允許來源的回應。但在需要憑證的跨來源請求中，不能把 `Access-Control-Allow-Origin: *` 與允許憑證讀取的設定隨意組合。伺服器應依允許清單回傳具體來源，並搭配適當的憑證政策。另一方面，即使服務端正確回覆了 CORS 標頭，瀏覽器仍可能因 Cookie 的 SameSite 或其他政策不傳送 Cookie。CORS 是一層規則，Cookie 是另一層規則。[B18][B19]

想像某網站登入時發了 Cookie，下一次 API 呼叫卻回 401。調查時至少要分辨：Cookie 是否被瀏覽器接受與儲存？此請求的域名、路徑、方案是否符合 Cookie 範圍？跨站情境中 SameSite 是否允許傳送？用戶端 `fetch` 是否設定合適的 credentials 模式？伺服器是否真的認得這個 Cookie？憑證是否已過期？若只在後端加上一行 CORS 標頭，卻不回答上述問題，通常很難恢復可用且安全的登入流程。

## 四、Cookie 的幾個屬性不是同一種防線

`Secure` 讓 Cookie 在適用條件下只透過安全方案傳送，降低被明文通道帶走的風險；`HttpOnly` 限制前端 JavaScript 直接讀取該 Cookie，可減少某些惡意腳本取得工作階段識別的途徑；`SameSite` 控制跨站情境中的 Cookie 附帶行為，常見值有 Strict、Lax、None，且 None 搭配 Secure 有其要求。`Domain` 與 `Path` 則影響在哪些主機或路徑範圍會附帶 Cookie。這些屬性可互補，但沒有任何一個能單獨取代完善的身分認證與授權。[B19]

尤其要區分**同源**與**同站**。CORS 按來源處理；SameSite 所說的站點關係不是直接照搬來源的三元組。在同一個可註冊域名之下的不同子網域，可能屬於同站卻非同源，具體判定還涉及方案等規則。若把兩者當一回事，設定跨子網域登入時就會出現令人困惑的結果：Cookie 可能被傳送，卻仍不能由某來源的 JavaScript 讀取 API 回應；反之，CORS 許可存在，Cookie 卻未附帶。

Cookie 也不應和 `localStorage` 混為一談。兩者都可能在瀏覽器保存狀態，但傳送機制、可由腳本存取的條件及安全暴露面不同。Cookie 可以隨符合條件的 HTTP 請求附帶；`localStorage` 不會自動附帶為 Cookie，若程式把憑證放在可被腳本直接讀取的位置，必須特別評估腳本注入風險。對登入系統而言，選哪一種狀態存放方式不能只看實作方便，還要看威脅模型、跨來源需求、伺服器端驗證及工作階段撤銷方式。

## 五、假設情境：網站與 API 分離後忽然無法登入

假設教學網站前端在 `https://learn.example.com`，API 在 `https://api.example.net`。管理員由同一套系統登入，瀏覽器卻得到 CORS 錯誤。可從時間順序梳理：頁面首先是否成功載入？登入請求是否觸發 OPTIONS 預檢？預檢回覆包含何種 Allow 標頭？實際 POST 是否發出？回應裡是否設定 Cookie？瀏覽器是否接受？隨後帶 Cookie 的請求是否被伺服器認證？如此便能把看似單一的「登入壞掉」分成不同可驗證環節。

如果只是在服務端對所有來源無條件反射 `Origin`，或把所有請求視為有權存取，雖可能讓畫面短暫正常，卻也可能把私人 API 暴露給惡意來源的讀取。合理做法是明確列出可信前端來源、驗證方法與標頭、為憑證請求套用適切規則，並在伺服器上對每次敏感資料操作執行真正的授權檢查。這是假設教學案例，並非對某個正在運作的服務做安全審核。

再假設使用者說「Chrome 可以登入，另一個瀏覽器不行」。不能直接推論另一個瀏覽器的 CORS 有問題。可能是 Cookie 政策差異、擴充功能、已保存的舊狀態、隱私設定或第三方嵌入情境造成。比對完整請求與回應、Cookie 是否被接受以及是否存在預檢，是比反覆刪除所有瀏覽資料更有價值的觀察。


## 補充：前端環境變數不是保護秘密的保險箱

跨來源設定排查時，有人會把 API 金鑰、長效登入憑證或管理密碼塞入前端環境變數，以為程式編譯後不容易被看見。實際上，任何必須送到一般使用者瀏覽器執行的程式與資料，都不應被當作只有伺服器知道的秘密。即使名稱寫著 `SECRET`，只要出現在可下載的前端資源或瀏覽器請求中，就應視為可能被觀察。應將需要保密的權限操作放在後端，並讓後端依實際使用者與業務規則驗證，不要僅依前端隱藏按鈕保護資料。

另一個容易出錯之處是錯把「登入成功」當成「任何 API 都有權呼叫」。登入證明請求者持有某種身分或工作階段，授權還要判斷該身分可讀寫哪些資料。例如學員能查自己的報名，並不代表能把查詢參數換成別人的識別碼就取得別人的資料。這是伺服器每個敏感路由都要落實的責任，無法由 CORS、Cookie 的 HttpOnly 或畫面上的登入提示單獨完成。[B17][B18][B19]

## 六、從常見誤解走向可驗證的安全設計

常見說法「前端把 CORS 關掉就能修」在網站部署時往往走不通：跨來源讀取是否允許主要取決於瀏覽器依服務端回應的檢查，而不是普通網頁腳本能任意停用。開發期間臨時放寬瀏覽器安全限制，只會造成本機和使用者真實環境不一致；若以公開服務維持此狀態，更可能帶來不必要風險。

第二種誤解是「CORS 設了指定網域，所以資料已安全」。不是。CORS 不是防止任何工具向 API 發請求的防火牆，也不是身份識別機制。敏感 API 必須保留伺服器端授權。第三種誤解是「使用者看不到 Cookie 值就不用擔心 CSRF」。HttpOnly 只限制腳本直接讀取，不表示任何利用瀏覽器自動附帶工作階段的攻擊都被消除；SameSite 等機制可降低部分風險，但仍應依交易敏感度與應用需求採取相應防護。

本章根據瀏覽器與 HTTP 技術文件解釋概念，沒有承諾特定瀏覽器版本永久採用完全相同的預設政策。網頁平台會持續調整第三方 Cookie 與隱私機制，實際故障需要核對當次使用的瀏覽器、嵌入模式、回應標頭和控制台提示。懂得把**同源、跨站、帶憑證、通過認證與獲准存取**分成五個不同判斷，才不會用降低安全性來換取一個表面的「問題已修好」。
