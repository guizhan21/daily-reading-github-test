# 第三章｜讓流程記住自己做過什麼：狀態、重試與可恢復執行

## 對話記得進度，不等於工作真正留下進度

某個任務需要依序讀入資料、檢查欄位、產生報表、寄送通知。系統已完成前三步，正在寄信時瀏覽器意外關閉。重新打開後，畫面上的對話可能還寫著「正在寄送」，但程式可能早已終止；也可能遠端服務已接受郵件，只是本機尚未收到回覆。若系統把聊天紀錄當作唯一進度，就無法分辨這些狀態。這不是語言理解能力不夠，而是持久化狀態與外部系統一致性的問題。

對假設教育團隊而言，核心的任務紀錄應是明確的實體。每次整理名冊建立穩定的 `job_id`，記錄發起者、範圍、輸入版本、目前階段、開始與更新時間、各步驟完成證據，以及最後輸出檔案的位置。使用者重新開頁面時，讀的是這份權威紀錄，不是靠模型推斷最後一句話代表什麼。若任務狀態說「報表已生成」，系統應能找到檔案並檢查檔案資訊；找不到就要顯示狀態不一致，而非繼續宣稱成功。

## 狀態機比「現在處理到哪」更精確

狀態機是一套有限、受限制的狀態及轉換規則。可以設計為：等待資料、資料已驗證、產表中、待人工核准、通知中、完成；另有失敗、取消、部分完成與等待外部恢復等分支。每次轉換不只是更新一個文字標籤，而應確認前置條件。例如「待核准」可以進入「通知中」，必須持有對應版本的核准結果；「資料驗證失敗」不得直接跳到「完成」。哪些狀態適用，要由實際任務設計決定，並沒有任何單一的 Agent 標準狀態表。

狀態機有兩個好處。第一是停機後能從正確的位置接續，而非重頭執行。第二是排除不合法跳轉。若某筆名冊仍在驗證中，卻出現「已通知全體」的事件，就能立即偵測流程或程式出了問題。這比對一段漫長聊天內容尋找「它是不是曾說過已經驗證」可靠。Temporal 的工作流程文件將可恢復執行與活動重試作為核心概念，但那是特定工作流程平台的能力說明；使用其他佇列、資料庫或自行設計狀態機也能實現相近目標，前提是持久化與恢復邏輯確實做對。[P08]

需要區分「任務」和「步驟」。任務代表完整的業務意圖，步驟是其中可驗收的單元。若生成 CSV 已成功，而遠端通知失敗，不必重新讀取和修改原始名單。將每一步成果關聯回同一個 `job_id`，就能只重做尚未成功的部分。這是把系統拆小的實際理由，不只是讓程式碼看起來整齊。

## 逾時、失敗與完成是三件不同的事

網路呼叫可能經歷五種情況：請求根本沒有送出；已送出但沒有到達；遠端收到並拒絕；遠端完成但回應遺失；遠端仍在處理。從本機看，有幾種情況都可能只顯示「等待太久」。因此，逾時只是「等待期限內未確認結果」，不是「操作一定沒發生」。如果重試的是只讀查詢，多半影響效能；如果重試的是寫入或發送，可能造成重複效果。

AWS 的可靠性指引把冪等性視為降低重試副作用的關鍵。冪等的意思不是「一定只跑一次」，而是同一個被辨識的操作即使重複提交，也不應造成重複業務效果。可透過冪等鍵將多次請求對應到同一件工作；服務端查到相同鍵時，回覆原來結果或目前狀態，而不重新插入一筆。[P07] 要做到這點，鍵必須在重試期間穩定。若每重試一次就生成新的識別碼，接收方只會看到不同操作，無法知道它們原本是同一個意圖。

假設寄送「提醒補件」時建立操作 ID `courseA-week3-user42-reminder1`。第一次請求逾時，第二次要沿用原 ID，並先查遠端服務能否支援冪等提交。如果遠端系統不提供相應能力，可以在本地維護待發送紀錄、取得服務端訊息 ID、做重複檢查；但若外部服務沒有可靠查詢介面，仍可能存在無法完全消除的不確定性。對這類情況，應保留「結果待核對」而不是宣稱百分之百恰好寄出一次。

Temporal 的技術文件特別提醒，即使工作流程平台會重試未確認成功的活動，活動本身也可能實際執行多次。例如外部服務已完成寫入，但工作執行者在回報完成前當機；重新執行時若沒有冪等機制，就會發生重複效果。[P08] 這提供了一個很重要的概念：工作流程的執行紀錄、真正的外部效果、以及使用者看到的成功訊息，未必天然同步。恢復機制要處理這個落差，而不只是重開一段對話。

## 重試需要規則，也需要停止條件

不是所有錯誤都值得重試。網路暫時不通、遠端服務短暫負載過高，可能適合有限次數的退避重試；登入失效、沒有權限、參數不合法、指定檔案不存在，則應停下並等待修正。Google Cloud Storage 的官方重試文件說明了哪些連線與伺服器錯誤可能重試、如何採指數退避，以及操作的冪等性如何決定重試安全性。[P09] 這是該服務的具體規則，不能直接套成所有 API 的通用錯誤碼政策，卻能示範「先分類錯誤再重試」的工程思路。

所謂指數退避，是連續失敗後把等待時間逐步拉長，而不是每秒打一次請求；若加入隨機抖動，還可避免大量客戶端同時再次衝向服務。退避仍需有最大次數、最大總等待時間，以及最終處理方式。若系統明明已收到權限拒絕，卻仍每隔幾秒重試，就是把確定性的錯誤當暫時性故障，浪費資源也可能增加安全警報。

即使遇到可能恢復的故障，也不應無限重做昂貴步驟。假設 AI 已花費算力產生一份長報告，只在下載階段逾時。若報告存在於遠端，恢復下載比重新生成更合理；要先查對應生成識別碼與檔案狀態，再判斷下載是否完整。這種設計同時降低成本與重複工作。真正可靠的系統，不是永遠不失敗，而是失敗發生後能知道哪些成果已被證實、哪些還需要確認。

## 不可逆動作需要預案，而不是僅靠復原按鈕

有些步驟可簡單重做，有些卻無法像檔案版本那樣回復。寄出的電子郵件不能真正「收回」至每個收件者的記憶；已公開的錯誤內容可能被截圖；錯誤的付款處理可能觸發後續帳務。對這些操作，單純在介面提供「上一步」不足以保障安全。應在執行前建立預覽、核准、目標限制與可追溯紀錄，並針對失敗準備補償措施。補償的意思是用另一個明確動作修正效果，而不是把時間倒轉。

例如名冊資料更新可以先保留舊版本，遇到不正確變更再回復；寄錯通知則可能要另外發更正訊息，這並不能抹除原通知已被看到的事實。跨服務任務中的補償設計，在分散式系統有相關的 Saga 模式，Temporal 的官方資料也討論了補償與恢復的機制。[P23] 是否需要這種複雜架構，取決於業務風險與跨系統程度，不表示每個小型自動化都應引入完整框架。

## 記錄與觀察不是同一件事

系統可以儲存一長串 log，卻仍不知道目前是否健康。真正可觀察的指標要對應使用者關心的事情，例如今天預期處理二十筆報名，已驗證幾筆、等待核准幾筆、失敗幾筆、最久等待多久。若只監控伺服器 CPU 是否正常，無法發現所有報名都卡在「待通知」的情況。AWS 的代理系統可靠性設計文件建議以持久訊息、檢查點與可恢復路徑控制失敗影響，這可視為架構設計方向，而非套用後就保證可靠的公式。[P21]

另外，進度顯示應實事求是。當狀態是「已送出外部請求、正在等待回覆」，畫面就不要寫「下載失敗」；當某個動作被安全驗證阻擋，也不能說「已完成」。對維護者而言，保留時間戳記、輸入版本、工具名、錯誤類別與來源 ID，才能在重啟後接續排查。對使用者而言，能看到哪一步卡住及是否需要介入，比一個永遠跳動的進度動畫更有價值。

## 真正的長任務是可保存、可恢復、可停止的流程

一個從開始到完成要花數十分鐘的 Agent 任務，不能只靠單一瀏覽器連線維持生命。任務管理者需要在持久儲存中記下工作、分派可執行的步驟，並能辨識工作者是否失聯、執行是否逾時、應如何恢復。需要取消時，也應清楚區分「不再開始新的動作」與「已提交外部系統的動作能否中止」。使用者按下停止，不應被系統解讀為過去的所有效果都已消除。

判斷流程是否可靠，最有效的方法不是只看一次成功畫面，而是故意在不同位置中止與重啟：資料讀完後關機、CSV 生成後斷線、通知送出後但回覆前中斷。每一次都觀察系統能否從已確認的狀態恢復，是否產生重複檔案與多餘通知，能否向使用者如實解釋。這類故障情境比單純「按下開始，等它成功」更能揭露工程缺陷，也為下一章討論讓模型何時決策打下基礎。
