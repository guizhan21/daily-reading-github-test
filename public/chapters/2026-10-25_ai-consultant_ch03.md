# 第三章　資料模型與遷移：最昂貴的錯誤往往不在畫面上

一張表單輸入的資料，只要沒有離開使用者的瀏覽器，修改欄位往往不難；當資料開始保存、被其他頁面使用、和外部帳號關聯、累積數月記錄之後，一個看似簡單的欄位改名就可能牽動整個系統。AI 可以替你產生新的資料表，卻無法只憑程式碼推斷歷史資料應該如何轉換。軟體工程之所以重視資料模型，是因為資料比介面更持久，也更難承受一次錯誤的刪除。

資料模型不是「欄位越多越完整」，而是對現實世界做出選擇：哪些事物需要各自的識別？事物之間的關係是什麼？哪些條件永遠不可同時成立？如果這些選擇不準確，前端的補丁只能暫時掩蓋問題。以下以假設的租屋管理平台為例，不代表特定專案已採用這套設計。

## 一、先決定何謂一筆資料，再決定如何存放

租客、房屋、租約、付款與維修請求看似都是資料，生命週期卻不一樣。房屋可以有多位不同時期的租客；租客可能更換房屋；同一房屋的不同期間有不同租約；一份租約會產生多期租金義務與數筆付款。一味把姓名、地址、起租日、房租、付款與維修全部塞在一張表，容易造成重複欄位與更新異常：更改房屋地址時，舊租約中的同一地址是否一起更改？如果每列都是一位租客，空屋時要不要保留一列不存在的租客？

較好的模型會根據實體本身及其關係安排資料。例如 `properties` 代表房屋、`tenants` 代表租客、`leases` 連接租客與房屋並標示期間，`rent_payments` 代表特定租金期別的支付事件。這不是唯一合理做法，且真實系統可能需要多租客聯名、分租單位與代理收款，但它迫使設計者清楚說明每張表所代表的事物。

一筆資料的識別碼應表達「這是同一個紀錄」，不要用容易改變的姓名或手機號碼充當穩定識別。姓名可能重複，手機可能換號，房號可能被重新編碼。識別碼也不應自動被當作存取憑證；即使 URL 裡有不可預測的長字串，仍需考慮哪些資料可以分享、哪些操作需要登入授權。

## 二、約束與交易是防止真實世界互相矛盾的工具

程式如果只在畫面上檢查「租金必須大於零」，另一個 API 或批次匯入仍可能寫入不合理資料。資料庫約束可以替長期不變的條件提供更靠近儲存層的保護，例如必要欄位不可為空、外鍵必須指向存在的紀錄、同一個外部付款識別不能重複。不是所有規則都適合單一 SQL 約束；跨時間區間、跨多筆業務狀態的規則，可能需要交易與應用程式邏輯共同保護。

交易（transaction）可將多個資料庫操作放進同一個全有或全無的單位。PostgreSQL 官方教學以轉帳為例，強調多個更新應同時成功或失敗，避免一方扣款但另一方未入帳；交易中尚未完成的變更也不應被其他交易視為已提交結果。[S07] 這種原理可用於報名系統：檢查剩餘名額、建立報名、調整名額計數三者若分離且缺少適當併發控制，就可能在大量同時請求下超賣。

然而「使用交易」不是解決所有併發錯誤的咒語。交易隔離等級、鎖定方式、資料庫約束與重試策略都會影響結果。若兩個請求都先讀到名額尚有一席，之後各自寫入，仍要依資料庫的隔離與更新設計檢查是否可能兩者同時成功。顧問應追問的是：當兩人同一瞬間爭取最後一席，系統有哪些可被資料庫強制維持的條件？而非只問「你有沒有包交易」。

## 三、重複請求不是例外，而是網路世界的基本情境

使用者送出付款或報名後，手機網路暫時中斷，並不等於伺服器沒有完成寫入。若重新送出會建立第二筆紀錄，系統就有重複提交的風險。所謂冪等性，是重複提出相同意圖時，不應造成意外的多次業務效果。例如把「本次送出請求」附上一個穩定的識別，後端識別已處理的同一請求並回覆原結果，可以降低重送造成的重複紀錄。實際實作還需決定識別有效期限、參數不一致時如何拒絕，以及併發請求如何避免同時越過檢查。

需要區分「請求重試」與「重新執行業務」。使用者今天新報名另一個活動，是新的意圖；同一個活動的送出按鈕因逾時重送，是原意圖的重試。若只用姓名當成去重條件，就可能錯誤阻止合法報名；若只靠按鈕變灰，使用者重新開頁或用其他裝置仍可能重送。穩定意圖識別、資料庫唯一約束與伺服器端結果記錄要互相配合。

外部通知使問題更複雜。資料庫交易提交成功，不代表簡訊、電子郵件與第三方支付會同步成功；反之通知成功後資料庫交易失敗，也可能讓使用者收到錯誤訊息。一種工程做法是把待發送事件與業務資料在同一資料庫交易中記錄，再由獨立程序發送；這能避免某些遺失事件，但不能保證外部收件方絕不重複收到。需要讓接收端或發送端也有去重能力，並能追蹤「等待、已發送、失敗」的狀態。

## 四、遷移是版本化的資料變更，不是點一下同步

假設原本付款表只有 `paid: true/false`，後來要支援部分付款、退款與爭議款項，便打算改成 `status` 欄位。若直接移除舊欄位，上線中仍在執行的舊版程式會讀不到欄位；若只新增欄位，歷史資料的狀態尚未轉換，報表就可能不一致。資料庫遷移需要考慮舊資料、新程式和正在運作的舊程式短暫共存。這也是為何不少資料庫變更會採用先擴充、回填、切換讀寫、最後收縮舊欄位的逐步策略。[S08][S09][S20]

Prisma 官方文件區分開發時建立遷移與在正式環境套用待執行遷移的命令；其 `migrate deploy` 文件並指出該命令不負責檢查資料庫漂移，也不會自動產生程式產物。[S08] 因此，看到「遷移成功」不能推論所有程式都相容，更不能推論資料已備份。不同 Prisma 大版本與新舊工作流程的命令可能不同，應以實際鎖定版本的文件為準，避免把某一版指令永遠硬寫在部署腳本。

Supabase 也提供以檔案追蹤遷移歷史的工作流程；官方文件提醒，一旦團隊採用遷移，直接在遠端資料庫手動修改結構，容易造成歷史不同步，後續部署產生衝突。[S09] 重點並非特定 CLI 名稱，而是資料結構修改應能被追蹤、在獨立環境重放，並能檢查與正式資料的相容性。

還有一個常被忽略的問題是資料語意會隨時間改變。假設早期的「已付款」只代表管理員手動勾選，後來變成第三方支付確認成功；若沿用同一欄位、不記錄來源，就很難在報表中區分人工紀錄與可對帳的電子支付。新版本可能需要額外記錄付款方式、外部交易識別、確認時間與異常狀態，並明示舊紀錄缺乏哪些資訊。資料遷移的責任不只是讓舊資料「塞得進去」新欄位，而是保留可被正確解讀的歷史意義。

此外，任何批次回填都要考慮中途失敗。一次處理所有紀錄看似簡單，但若更新量大、鎖住重要資料表或因逾時中斷，可能影響正常服務。工程上可以依資料量和資料庫能力選擇分批、可續跑與記錄進度的方式；每一批仍需驗證結果，不能只因腳本印出「完成」就假設整批資料一致。

## 五、備份、回滾與修復不是同一件事

部署網站的舊版本很快，資料庫卻可能已被新版本寫入新的格式。即使程式回退，舊程式也可能不認得新的資料；若遷移執行了破壞性更新，簡單地還原 Git 程式碼不能找回資料。這說明三件事需要分開準備：一是備份能否恢復資料，二是應用程式能否在過渡期間相容，三是發生錯誤後怎樣補償已發生的業務事件。

備份是否真的有用，要看是否試過恢復、恢復到什麼時間點、會遺失多少資料、恢復需要多少時間。截圖或 Excel 匯出可能保存部分內容，卻未必能完整還原關聯、權限政策、索引與附件檔案。對一次性活動的低風險示範，可接受的恢復條件與持續收租平台完全不同。規劃必須根據損失後果，而不是套一份固定容量表。

設計資料模型時也要保留刪除的語意。把租客從後台隱藏、標記為停止租用、依法刪除個人資料，是不同操作。資料庫的外鍵若要求關聯租客存在，直接刪除可能失敗；若設成連帶刪除，可能意外移除歷史帳務。每一個刪除動作都應說明對關聯紀錄、報表、附件與恢復路徑的影響。真正可靠的「刪除」往往需要更明確的業務政策，而不是更簡短的 SQL。

從顧問角度看，資料模型的成果不是畫出最華麗的 ER 圖，而是能向非技術人員說清：一筆資料代表什麼、如何從建立走到結束、誰能更改、有哪些不容違反的規則，以及改版是否傷害過去資料。這些問題一旦有一致答案，AI 才可能在清楚的限制下有效協助設計、產生與檢查遷移程式。
