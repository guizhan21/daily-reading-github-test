# 第二章｜工具呼叫與執行邊界：模型提出請求，系統承擔動作

## 「使用工具」其實是一次跨越邊界的交接

當語言模型說「我將更新報名資料」，這句話仍是文字。要讓外部世界真的改變，系統必須接收某個可執行的請求，檢查參數，呼叫資料庫或服務，再把真實結果送回模型。Anthropic 的官方工具使用文件明確區分兩種環節：在由客戶端執行的工具中，模型產生結構化請求，應用程式實際執行並回傳工具結果；另有部分由服務提供方代為執行的內建工具。因而不能籠統地說所有工具都在模型內部執行。[P03] 這個區別決定誰能檢查權限、誰負責重試以及失敗記錄放在哪裡。

對教育團隊的假設報名系統而言，一個工具可能叫 `list_enrollments`，只允許查詢指定課程的報名資料；另一個叫 `mark_payment_reviewed`，會改變某一筆審核狀態。前者讀取資料，後者寫入資料。若都只用模糊的 `manage_students` 名稱包在一起，模型與工程師將難以判斷哪次呼叫有副作用。工具的設計應先由業務動作與權限界線出發，而不是把整個後台介面暴露出去，再期待模型自行克制。

## 把人話拆成可以驗證的資料契約

工具呼叫需要合約：名稱、功能描述、必要參數、資料型別、允許值、輸出形狀、錯誤狀態。假設查詢報名名冊需要 `course_id`、`status` 與 `page_size`。`course_id` 應是系統能辨識的課程代碼，而不是模型自行想出的課名；`status` 應限制在明列的值；`page_size` 應有上下界。若缺少課程代碼，正確行為不是猜一個，而是回覆條件不足，或透過受限查詢取得可選課程。這些檢查應落在執行端，而不是只寫在說明文字。

OpenAI 的 function calling 文件描述了在工具定義中使用結構化參數與 `strict` 模式的方法。嚴格模式可以讓受支援的工具呼叫遵守所提供的 JSON Schema 子集，但它有明確的 schema 條件與相容性要求；例如物件通常需禁止額外欄位並標示必要欄位。[P02] 這是格式約束，不是商業事實的證明。即使模型產生一個合法的 `course_id` 字串，該課程可能不存在；即使參數符合 `amount` 是數字，也不能證明金額計算正確。合乎 schema 只是第一道門檻。

同樣地，回傳格式也需要明確。查詢工具不應只回「已找到很多報名資料」，而要包含結果筆數、是否還有下一頁、時間範圍、資料來源版本、必要的識別欄位及失敗代碼。若把超大量個資原樣塞回模型，成本與洩漏風險會增大；可先由程式只整理完成任務所需的欄位。若有欄位被遮蔽，回傳結果應明示遮蔽，不應讓模型猜出缺漏內容。工具輸出是資料而非指令，這條界線對後續安全章節十分關鍵。[P10]

## 模型建議執行，不代表擁有執行權

真實服務的授權要至少問三個問題：現在是誰提出需求？這個人有權操作哪個對象？這個動作在目前狀態下是否合法？假設一般助教能檢視自己課程的報名名單，但不能刪除付款紀錄，那麼無論模型提出多麼合理的刪除理由，伺服器都應拒絕。若使用者只要求「顯示尚未付款的名單」，程式也不應把這句話解釋成「可以自行變更付款狀態」。權限判斷要根據可信的登入與授權資訊，而不是採信模型在文字中填入的角色。

可以把工具執行想成銀行櫃台：顧客說得清楚，不代表交易被允許。櫃台有操作規則、身份驗證與交易記錄。這是權限分離的比喻，不表示銀行與 AI 系統具有相同技術架構。對 AI 工具而言，真正的「櫃台」是應用程式控制的執行層，它檢查模型建議的操作、參數、使用者權限與交易前置條件；未通過就不能執行。AWS 的代理可靠性文件也主張以狹窄、可測試的能力與最小權限降低模型決策造成的衝擊。[P12]

對會修改內容的工具，還需要分開預覽與提交。`preview_enrollment_changes` 可以計算將新增、覆蓋、刪除哪些紀錄，但不實際寫入；`commit_enrollment_changes` 則只能依有效的預覽版本與核准資訊進行提交。若預覽之後原始資料又被別人修改，提交應拒絕或要求重新核對。這個設計將語言理解、資料計算、正式變更各自放在可追蹤的位置，也讓批准的人知道自己同意的是哪個版本。

## MCP 是連接協定，不是自動授權證書

Model Context Protocol，簡稱 MCP，是描述 AI 應用如何與外部服務交換工具、資源及提示相關訊息的協定。其 2025 年 11 月 25 日版工具規格定義了列出工具、呼叫工具、輸入與輸出 schema 等機制，並特別指出工具註記若不是來自可信伺服器，客戶端應視為不可信資訊。[P04] 換句話說，看到一個工具宣稱自己「唯讀」或「安全」，不等於實際執行時必然只讀。協定讓介接方式更一致，卻不能憑空提供每個工具的實際安全保證。

MCP 的主機、客戶端與伺服器是不同責任。主機整合使用者互動與模型；客戶端建立到指定伺服器的連線；伺服器提供功能與資料。這些是協定架構角色，不能直接推導某個第三方伺服器一定可信。假設教育團隊把報名系統接到外部 MCP 伺服器，必須仍然確認它取得哪些資料、請求會送往哪裡、誰能查詢及紀錄保留多久。[P05] 在另一個情境中，直接呼叫團隊已掌控的後端 API，可能比多加一層通用協定更容易審計；選擇要看維護與整合需要，而非跟隨名稱熱度。

MCP 的 HTTP 授權規格描述了受保護伺服器如何透過 OAuth 類機制處理授權，同時明確區分 HTTP 與本機標準輸入輸出的適用情境。它不代表啟用 MCP 便自動完成登入、權限分級或資料保護。[P20] 應用仍須實作所需的身份、授權範圍、憑證保存、網路安全與稽核。若你的系統其實只要讀取一個受控資料庫的少量欄位，沒有必要因為「Agent 最流行 MCP」就讓它取得所有雲端資料與檔案寫入權。

## 錯誤回報必須比「失敗了」具體

工具失敗可能有非常不同的成因：參數格式錯誤、沒有授權、資源不存在、外部服務超時、資料庫鎖定、檔案損毀、版本衝突。若全部回報成「請重試」，模型可能一再提出相同的無效呼叫。更合適的合約是讓每個錯誤附上類型、能否重試、是否發生任何副作用，以及供系統追查的執行識別碼。這是本書提出的設計方法，不表示某個工具協定已要求全部採用這些欄位。

尤其是超時。假設寄信 API 在服務端已接受請求，但網路回應丟失；本機只看到「逾時」，不能判定信件沒有寄出。若直接重送，可能產生兩封。正確的下一步是用原操作識別碼查詢狀態，或使用服務支援的冪等機制，而不是把等待逾時直接當作失敗。AWS 對分散式系統冪等操作的指引特別強調：重試前應能辨識這是不是同一個請求，避免相同操作被執行多次。[P07]

同理，工具成功回傳也不一定是業務工作完成。匯入名冊 API 回「200 OK」可能只代表請求已被伺服器接受；還須檢查是否真正寫入、總筆數是否吻合、失敗紀錄是否列出。若某個 API 是異步處理，應有「已接受」「處理中」「完成」「部分完成」「失敗」等明確狀態。不要讓模型自行把它們揉成一個「完成」字眼。

## 把能力縮小，才能更放心地擴大使用範圍

安全的工具設計並不等於功能少，而是每個功能所承擔的責任小而清楚。對假設教育團隊而言，第一組工具可以只有查詢名冊、檢查欄位、產生預覽和下載匯出檔四種。稍後才加入更新資料與發送通知。每加入新工具，就重新確認它允許哪些輸入、是否會產生外部效果、有哪些可預期失敗，以及誰能看到結果。

真正考驗設計的往往是多人同時操作。假設兩名助教同時整理同一門課，一個人的畫面還顯示舊版資料，另一個人已完成訂正。如果工具只收到「把這筆改成已核對」，卻沒有附上它認定的原始版本，較晚送出的操作可能覆蓋較新的判斷。為降低這種風險，可以要求提交時提供預期版本號；當權威資料版本不一致，工具就回覆衝突並保留雙方差異，而非默默選擇最後一個寫入的人。這種版本檢查屬於資料系統的一般工程方法，並不是模型額外掌握的一種神奇能力。

此外，應把日誌分成可供使用者理解的操作紀錄與供維護者排障的技術紀錄。使用者需要知道「誰在何時針對哪一份名冊提出修改，最後結果是什麼」，維護者則可能需要請求識別碼、工具版本與錯誤分類。兩者都不應無限制儲存學員的全部個人資料。過量記錄會增加洩漏面；過少記錄又無法釐清事故，因此保存範圍和期限應依真實風險設計。

這種做法的成本是設計時間與額外驗證，但收益是較容易排查錯誤、縮小事故範圍，也比較能向使用者解釋系統做了什麼。語言模型負責把需求轉換成候選動作；固定程式與權限服務負責決定能不能做；真實資料與測試負責證明做成了沒有。當這三者的位置清楚，下一個問題就是：任務跨越多個步驟、甚至超過一次執行生命週期時，系統要靠什麼記住進度？
