# 第四章　頁面已回覆，事情卻沒完成：HTTP 與快取的真正語意

「網頁打開了」常被誤認為整個網站已恢復。可是首頁能載入，不表示購物車能結帳；API 回傳 200，不表示資料已寫入；新版本已部署，使用者卻看到舊介面，也不一定是部署失敗。要理解這些看似矛盾的情況，必須認識 HTTP：一套讓客戶端與服務端交換請求及回應的應用層協定。它定義方法、狀態、欄位與表示資源的方式，但不會替業務流程完成最後一公里。[B14]

## 一、請求與回應是一場有格式的問答

HTTP 請求有方法、目標與標頭，也可能包含內容；回應帶有狀態碼、標頭與回應內容。`GET` 通常表示取得目標資源的目前表示，`HEAD` 可取得類似 GET 的中繼資訊而沒有回應內容，`POST` 表達交由目標資源處理所提交資料，`PUT` 以指定表示建立或取代目標資源，`DELETE` 請求移除目標資源的關聯。這些方法包含協定層的語意，卻不強迫每個網站都採用完全一致的業務命名。[B14]

對寫網站的人而言，方法語意不只是「按鈕應該用哪一種」。GET 被定義為安全方法，意即客戶端不要求以它來改變伺服器狀態；這不代表伺服器不會記錄日誌、統計流量，而是業務端不應把付款、刪除等有意副作用藏在普通 GET 裡。當你把「刪除報名」設計成開一下網址就執行，外部預覽器、快取、瀏覽器預讀與使用者分享連結都可能變成意外觸發源。這類錯誤是應用設計違背語意，不是網路本身在亂做事。

**冪等性**則是在相同請求重複套用時，預期的效果與套用一次相同。依協定語意，PUT 與 DELETE 可具冪等性；POST 通常不能直接假設如此。假設一個表單送出訂單後，網路斷線使前端不知道回覆是否到達。若直接重新送相同的「建立訂單」請求，可能重複產生記錄。正確設計可用業務層唯一請求鍵、狀態查詢與後端交易控制處理，但這是應用的補強機制，並非瀏覽器會自動保證「按兩次只存一次」。

## 二、狀態碼不是診斷書

HTTP 狀態碼分成資訊、成功、重定向、客戶端錯誤與伺服器錯誤五大類。`200 OK` 說明就 HTTP 層而言請求成功；`201 Created` 可表示資源已建立；`204 No Content` 表示成功但沒有回應內容；`301` 與 `308` 等用於重定向，帶有各自的方法保留或永久性語意。這些狀態能幫助客戶端理解回應類型，但「HTTP 成功」和「使用者想完成的事已成功」仍是不同層次。[B14][B23]

`404 Not Found` 的意思，是伺服器沒有找到目前的目標資源表示，或不願透露它是否存在；它不必然表示整台網站主機離線。舉例而言，首頁 `/` 可以回 200，而尚未部署的 `/admin/orders` 回 404。如果錯把 404 當成 DNS 問題，就會去修改網域，反而破壞本來正常的首頁。`401` 與 `403` 有不同的授權語意，網站可以因安全需求選擇不揭露某些資源存在，但不能只靠錯誤碼推論帳號是否被封鎖。[B14]

`500` 表示伺服器遇到未能完成請求的狀況；`502 Bad Gateway` 是閘道或代理在向上游取得回應時接到不合格回覆；`503 Service Unavailable` 可代表暫時無法服務；`504 Gateway Timeout` 與代理等待上游逾時有關。這些規範性定義是判斷方向，不是自動找出哪個函式有錯。特定 CDN、平台和應用有時還會用自己的錯誤代碼或頁面，必須辨認回應究竟由哪一層產生。[B14]

## 三、重定向不是單純換一個畫面

從 `http://` 轉到 `https://`、從沒有 `www` 轉到有 `www`、從舊活動頁轉到新活動頁，都是重定向的典型用途。客戶端接到重定向後，可能需要再對新網址發出請求。若新位置指向錯誤域名、又轉回舊位置，就形成循環；若表單的 POST 遇到改變方法語意的重定向，還可能影響資料提交。不同狀態碼對方法與主體的處理有不同要求，不能把所有 3xx 當成可互換的「跳頁」。[B14]

還有一個常被忽略的安全面向：網站登入後若接受任意 `redirect` 參數，直接將使用者送往外部網址，就可能成為釣魚流程的一部分。這和 HTTP 重定向機制本身沒有矛盾；問題出在應用沒有為轉向目標建立合理限制。真正的工程工作不只是令瀏覽器會跳，而是決定什麼條件下、能跳去哪裡，以及使用者是否能辨識變化。

## 四、HTTP 快取的核心問題是「什麼時候可以重用」

快取不是「瀏覽器自己亂記」。HTTP 快取有可被規範描述的存取與驗證行為。回應可能包含 `Cache-Control`，告訴快取能否儲存、在何種條件下可被視為新鮮、是否需向伺服器再驗證。`max-age` 表示新鮮度上限，單位是秒；`no-cache` 名稱容易讓人誤解，它並不是「完全不可儲存」，而是在重用儲存回應前必須通過再驗證；`no-store` 則指示快取不要儲存該回應。規範有不同適用條件，還包含共享快取和私人快取的差異。[B15][B16]

一個網站更新前端 JavaScript，卻仍有人看到舊版，可能與瀏覽器快取、CDN 快取、HTML 與靜態資源的版本策略不一致有關。例如內容摘要雜湊放進檔名的資源，改了內容就會換網址，適合搭配較長期快取；會一直更新且網址不變的 HTML 則要設計合適的再驗證策略。這是常見工程安排，不意味著所有託管平台都採相同標頭；最後仍要看實際回應中的 `Cache-Control`、`ETag` 等欄位。

## 五、ETag、304 與「沒下載新內容」的不同意義

伺服器可用 ETag 代表某一表示的驗證識別。客戶端手上已有先前版本時，可以帶上條件請求，例如 `If-None-Match`；若相應條件成立，回應 `304 Not Modified`，客戶端便可以再使用已有內容，而不必重新傳完整主體。這能節省資料傳輸，但只有在伺服器與快取正確建立版本一致性時才可靠。`304` 也不是業務資料「沒有變動」的通用保證，它只涉及被驗證的特定表示。[B14][B15]

若管理員急著處理故障，使用瀏覽器的強制重新載入可幫助觀察快取差異，卻不該直接把「強制刷新後好了」當成完整修復。它可能只讓這台設備暫時取得新檔案；其他使用者、CDN 或服務工作者仍可能持有舊版本。如果問題重複出現，應比較快取策略與版本資源引用是否一致，而不是要求所有訪客永久手動清除資料。

## 六、假設情境：管理頁面顯示「儲存成功」卻沒有新資料

假設一個報名後台按下儲存，頁面彈出「成功」，但刷新列表後仍顯示舊值。可能的情況至少有四種：前端根本沒有發出更新請求；請求發出了但伺服器拒絕或失敗；伺服器已更新而讀取端查了另一份資料；列表拿到的是快取或陳舊狀態。要區分它們，第一步是在瀏覽器檢視網路請求，確認實際方法、網址、狀態與回應內容；第二步才是比對後端記錄、資料庫寫入結果與重新讀取路徑。不能只根據前端跳出的提示推定資料已持久化。

這是**假設的診斷案例**。若 API 返回 200，但回應內有 `{"ok":false}`，說明 HTTP 請求從傳輸與協定觀點可能已成功，而應用內容表示業務失敗。這樣設計雖可以存在，但對監控、客戶端錯誤處理與可靠性不一定理想。更清晰的系統應合理利用 HTTP 狀態與結構化錯誤訊息，讓網路層和業務層的結果都能被追蹤。

另一個假設是部署新網站後，首頁可見新版本，但子頁功能仍使用舊程式。可能是舊 JavaScript 資源仍被快取，或不同請求由不同部署處理；也可能是環境變數、API 路由與資料庫設定不同。這些都需要具體請求證據。若把所有「舊畫面」一律判成快取問題，真正的環境配置失誤就會被延誤修復。


## 補充：快取設計也涉及資料隔離

快取若只考慮速度、不考慮回應內容是否專屬於某位使用者，可能造成比舊畫面更嚴重的問題。假設管理頁面的回應包含某位用戶的私人報名資料，卻被錯誤配置成可供共享快取重用，另一個符合相同快取鍵的請求就可能取得不該分享的內容。HTTP 快取標準會處理共享快取與驗證、認證請求的限制；但系統設計者仍須按內容敏感度設定合適的 `private`、`no-store` 等策略，並檢查中介設備是否依預期執行。[B15][B16]

快取鍵也不一定只有網址。當一份回應隨請求標頭而改變，`Vary` 能讓快取辨識哪些請求欄位影響表示版本；如果忽略語言、壓縮方式或其他必要差異，同一網址就可能回錯版本。因此「加了 CDN 就會自動又快又正確」不是可接受的設計假設。速度優化若破壞資料隔離、登入狀態或版本一致性，代價通常比幾十毫秒的延遲更大。

## 七、快取與狀態碼的適用界線

HTTP 標準告訴我們各狀態碼和標頭應如何被理解，卻不會保證所有服務、代理和客戶端實作都正確遵守，也不指定網站的商業交易該如何驗收。某次實際 API 的回應，即使符合協定語意，仍可能含有錯誤資料；某次被快取的資源即使在有效期內，也可能因部署流程不當而與另一個新資源不相容。因此，測試不應只檢查「是否回 200」，還要檢查內容、來源版本、授權和預期副作用。

本章的工程價值在於為「頁面有回應」建立更細緻的語言：HTTP 層成功、資源表示有效、版本一致、業務狀態已更新、下游系統也能查到，是不同證據。只知道狀態碼不夠，但不知道狀態碼的協定意義，就更難合理地解讀瀏覽器與伺服器正在發生什麼。
