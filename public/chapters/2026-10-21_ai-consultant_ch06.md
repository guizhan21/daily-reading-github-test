# 第六章｜從演示走向可靠交付：評測、追蹤與成本效益

## 一次成功，證明的事情其實很少

在展示影片中，代理收到要求、查詢資料、產出文件，最後說「已完成」。這可以證明在當次環境下某條路徑成功，卻不能回答更難的問題：換個說法還能完成嗎？缺少資料會不會猜？使用者沒有權限時是否會停下？網路逾時會不會重複寄送？輸出檔案是真的可用，還是只有畫面看起來像成功？真正的交付需要把這些問題轉成測試，而不是靠一次漂亮的展示讓人相信整個流程成熟。

對假設教育團隊，可先明確定義任務成功：匯入正確版本的名冊、保留每筆資料來源、辨識重複和衝突、產生可讀的檔案、在未核准前不發送通知。然後設計測試案例，而不是先挑模型容易做對的樣本。測試應包含正常資料、缺欄位、重複記錄、版本衝突、錯誤付款聲明、外部 API 逾時、權限不足，以及來自學員備註的提示注入。每個案例都有預期結果，才知道系統是否真的做對。

OpenAI 的評測文件把評估定位為檢查模型輸出是否符合事先指定的內容或風格要求，但對 Agent 工作而言，還必須加上工具使用、資料狀態和外部效果的驗證。[P17] AWS 的代理效能指引把延遲、吞吐量、品質與效率分開，並將任務完成、工具選擇及參數正確性納入品質考量。[P22] 這些都說明：只評價最後一句回答，不能完整評價一套會執行任務的服務。

## 把評測拆成四個不同的層次

第一層是理解：模型有沒有正確辨識使用者意圖與缺少條件？例如「我要查上週報名」是否應先確認班別與日期。第二層是操作：是否選對工具、帶對參數、遵守可用權限。第三層是結果：真實檔案與資料庫狀態是否符合預期。第四層是治理：遇到高風險或資訊不足時，是否適當停止、記錄、交給人處理。把這四層分開，才容易找出錯誤究竟出在模型判讀、工具設計、資料品質、執行器或審批流程。

假設一份測試集中有四十個條件完備的名冊匯出案例，三十五個完全正確，五個有錯；另有十二個刻意缺資料的案例，其中十一個如預期要求補件，只有一個擅自猜測；還有八個含惡意備註的案例，系統全部擋下不當工具呼叫。這些數字純屬教學假設，不是任何模型、組織或產品的實測。各類可分開表示為三十五除以四十、十一除以十二、八除以八，卻不能把三個比例直接平均成「整體準確率」，因為案例的重要程度和預期行為不同。

尤其要注意「安全停止」不是一概算失敗。若資料缺少收款證據，系統停止修改付款狀態，這可能是正確結果；若所有正常資料都因過度謹慎而不處理，系統則失去效用。因此測試集應事先標明每筆是要求完成、要求澄清、要求拒絕，還是要求人類核准。否則開發者可能為追求高完成率而讓系統冒險，也可能為追求低事故率而讓系統什麼都不做。好指標必須同時反映任務效用與風險限制。

## 不同測試要對應不同失敗模式

對工具呼叫，檢查工具名稱與參數是否正確；對檔案匯出，檢查存在性、編碼、欄位、資料筆數與內容；對寄送流程，檢查提交狀態與操作識別碼；對權限，嘗試使用無權限帳號；對恢復，刻意在步驟間中止執行。只有當測試涵蓋真正的失敗方式，通過率才有意義。固定的「黃金測試集」適合每次更新重跑；也需要逐步加入真實事故中發現的新案例，避免系統只對舊考題表現良好。

測試資料本身要管理版本。假設某天補課規則已更新，但測試答案仍沿用舊規章；模型照新版回答反而被判錯，那不是模型退化，而是評測資料落後。每一筆重要案例應能對應適用的業務規則與日期。若評測由另一個模型執行，也要檢查評分標準是否清楚，並在爭議案例中抽樣人工審查。模型給出的自信評語，不是客觀證明。NIST 的 AI 風險管理 Playbook 把衡量與管理放進完整治理流程中，並強調應依不同情境取捨措施，而非照單全收。[P16]

安全測試也要同時看是否造成真實副作用。一個代理最後回答「我拒絕匯出個資」，但在此之前可能已呼叫過外部寄送工具。若只收集最後文字，會把危險行為算成通過。這正是需要執行追蹤的原因。OpenAI Agents SDK 的追蹤文件描述了模型生成、工具呼叫與交接事件等紀錄方式，同時提醒紀錄可能含敏感資料。[P14] 因此追蹤既要足以重建執行流程，也要對個資與祕密做遮蔽，並控制誰能查閱。

## 上線前後不是兩張互不相干的成績單

上線前評測回答「目前版本是否符合預設需求」；上線後監控回答「實際使用情境是否正在變化、是否出現新失敗」。用戶的表達、資料欄位、供應商介面和權限政策都可能改變，讓原本通過的案例逐漸失效。AWS 的持續代理評估文件指出，上線後若缺少連續觀測，資料、模型與使用模式的變化可能讓品質下降而不易察覺。[P18] 這是設計持續驗收的理由，但不能由此推論某個具體供應商的模型一定會在某一天退化。

監測時可以將故障分成幾條線：使用者請求未完成、第三方工具不可用、資料品質下降、越權或異常呼叫、平均等待變長、成本升高。每個警報應能指向負責人與處理動作。如果某段時間的等待增加，可能是外部服務延遲，也可能是模型選擇太多無效工具；沒有逐步追蹤，就無法判斷該提高主機資源、修改提示詞還是減少工具路徑。監控不是把所有指標放上儀表板，而是讓問題發生時能定位原因。

正式部署也要有版本控制。當模型、提示詞、工具 schema、資料庫欄位或權限設定改變，應保存本次部署版本並重跑關鍵回歸測試。若更新後正常請求開始失敗，要能回復至先前可用版本；然而回滾程式不等於回滾所有已經發生的外部動作，因此仍要有資料遷移及補償安排。不要把「程式能重新啟動」冒稱「系統可以安全恢復」。真正的回復測試要確認輸入、狀態、輸出與權限在中斷後仍一致。

## 成本計算要以成功工作為單位

對企業導入而言，單次模型呼叫便宜不等於整套流程划算。完整成本包含模型輸入與輸出、工具服務、儲存與網路、人工審核、失敗重試及維運。假設一個月執行一百件任務，直接技術支出合計二百四十元，其中八十六件完成並通過驗收，九件正確地停下要求人工補充，五件產生需修正的結果。這是教學假設。若只計已驗收完成件數，直接技術成本約是二百四十除以八十六，也就是每件二點七九元；但這個數字尚未包含人工處理九件待確認和五件修正工作的成本。

同時應衡量原本人工流程耗時多少，以及引入系統後省下的時間是否被審核和排障抵消。對簡單且規則固定的任務，純程式批次處理可能比模型代理更便宜、更穩定。對需要閱讀非結構化文件的任務，模型可以減少初步整理時間，但應看重複使用後的效果，而不是只拿最佳案例比較。Anthropic 也提醒代理式系統會在彈性與成本、延遲之間產生取捨，應從最簡單可行方案開始。[P01]

價格與配額會變動，不宜在一本原理書中塞入未即時確認的各平台費率，更不能把模型成本等同總成本。若要向客戶提出方案，應在提案當天查核實際服務價格、地區限制與資料處理條件，再按照任務量、平均工具呼叫數與異常比率做情境估算。估算必須標示假設，日後用正式流量校正，不應把試算表上的預測寫成已實現的效益。

## 交付物必須足以讓別人接手

一套可交付的自動化服務，不能只有一段提示詞和一支成功影片。至少應具備任務邊界說明、資料來源與欄位契約、工具及權限清單、可驗收的完成條件、錯誤分類、重試與恢復規則、版本紀錄、評測結果、監控方式與異常處理責任。這些不一定要寫成厚重文件；重點是使用者和後續維護者能依資料做出判斷，而不必依賴原開發者口頭解釋。

面向非技術使用者時，交付說明還需要回答具體問題：什麼情況可以放心自動執行？出現「等待資料」或「權限不足」該找誰？哪些資料會保留？出錯如何停止？何時需要人工核准？講師或顧問若能把這些事項說得清楚，比單純展示模型能連接十幾個工具更有專業價值。這不是以文件取代系統，而是讓系統的責任、能力與限制對使用者可見。

本書真正想建立的能力，是把「AI 能替我做很多事」轉化為一套可以驗證的工程語言：需求可拆解、工具可限制、步驟可恢復、風險可控制、結果可查核、成本可比較。模型可能擅長提出下一步，但只有完整的執行與治理設計，才能讓完成的工作在離開展示情境後繼續成立。
