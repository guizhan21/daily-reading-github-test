# 第六章　不要再靠猜：用分層證據找出網站故障

建置網站的人最怕的不是看見錯誤，而是錯誤只偶爾出現。你在自己電腦上看見正常頁面，別人卻說進不去；昨天還能下載 ZIP，今天同一條下載連結失效；部署平台顯示「成功」，進入功能頁卻得到 500。這些問題沒有一個萬用按鈕能解決，但可以用相同的思維處理：先界定究竟是哪個命題失敗，再用最少的觀察排除最多不相干的可能，避免在沒有證據時同時改動 DNS、程式碼和憑證設定。[B20][B22]

## 一、先定義「壞掉」的最小可重現描述

「網站壞掉」不夠具體；「在 2026 年某日、某瀏覽器、某條網路，開啟特定 URL，主頁正常，但按下上傳後回覆 403」才是可測試的敘述。事件紀錄至少應包含發生時間與時區、完整但已去除敏感資料的網址、裝置與瀏覽器、當時網路、預期動作、實際結果、是否能重現、是否從最近更新後開始。若無法重現，也要保存使用者回報時的畫面、錯誤碼及請求識別，不要任意要求使用者提供密碼、登入 Token 或私人內容。

接著把訪問路徑切成層次：名稱能否解析？可否到達服務？傳輸握手與 TLS 能否完成？是否取得 HTTP 回應？狀態碼和內容正確嗎？前端有沒有成功執行？後端資料是否真的寫入？只有找到「上一層確認成功、下一層開始失敗」的交界，後續動作才不會變成無方向的猜測。這種分層不是要每次都把所有層完整測一輪，而是挑出最能區分假說的步驟。

如果所有網站都上不了，先檢查本地網路和設備比調整自己的站點更合理；如果只有一個網站的某個 API 出錯，就不必第一秒去重啟家中路由器。若同站多個使用者在不同網路都報一樣的 500，伺服器端路徑的優先度就提高。這些只是依證據排序的假說，不是概率保證；一次觀察不足以做最終因果推論。

## 二、把瀏覽器 Network 當作時間線，而不是紅字蒐集器

Chrome DevTools 的 Network 面板可以記錄頁面載入及後續操作造成的資源請求。官方教學指出，每一列通常代表一項資源或請求，開啟細節後可看 Headers、Response、Initiator 與 Timing。這些欄位回答不同問題：Headers 讓你確認目的地、方法、狀態與快取／跨來源政策；Response 告訴你伺服器實際回覆什麼；Initiator 有助追出哪個程式或資源引發此請求；Timing 則把等待分成可觀察階段。[B20]

對前端按鈕沒有反應的情況，先在 Network 打開並保留紀錄，再執行同一動作。若完全沒有預期的請求，問題可能在事件處理、前端檢查或程式執行階段；若請求出現卻被瀏覽器擋住，要區分混合內容、CORS 與安全政策；若確實發出並回 4xx，優先檢查路徑、認證、授權或輸入；若回 5xx，查服務端日誌與上游依賴。如此能避免看到一行紅色錯誤，就在毫不相關的地方修改 DNS。

Network 的暫時儲存可能涉及敏感資訊。若要分享 HAR 或截圖給他人協助，應先檢查是否含 Cookie、Authorization 標頭、查詢中的 Token、表單資料、個人姓名與聯絡方式。修網站不能以暴露使用者資料為代價。對外討論只保留可定位問題的最少資訊，必要時使用假資料重現。這是技術上能做到、也應納入工作流程的基本衛生。

## 三、DNS 查詢與部署平台要交叉對照

在 Windows 上，`nslookup example.com` 可取得預設 DNS 解析器對指定名稱的回答；也能指定另一個解析器協助比對。Microsoft 官方文件說明它用於診斷 DNS 基礎設施，並列出不存在名稱、逾時和伺服器失敗等不同錯誤。這讓「DNS 不正常」從一個形容詞變成可記錄的查詢結果。[B21]

若你使用託管平台，需要再看平台對自訂網域提供的預期 DNS 記錄。Vercel 官方排障文件要求檢查域名是否加到專案、記錄是否符合平台提示、名稱伺服器委派是否正確、是否存在憑證簽發相關限制。[B06] 許多開發者會拿從網路文章抄來的 A 記錄當標準答案；這不如看自己的專案目前應有的配置，因為各種服務、時期和產品方案可能不同。

**部署完成**與**流量已進入正確版本**也不同。部署服務可能已成功建置一個版本，但正式域名仍指向另一個部署、舊分支或尚未指派的專案；一條預覽網址能開啟，不能證明正式網域也會到達同個版本。若問題始於最近部署，應保存部署識別、Git 提交識別、建置日誌、環境變數的存在與作用範圍；但不得把秘密值直接貼到聊天或公開工單。Vercel 的建置排查文件聚焦建置階段的錯誤，與運行階段的 API、DNS 或憑證故障不是同一類問題。[B22]

## 四、錯誤碼先分清由誰發出

狀態碼提供初步方向。`404` 常見於請求資源或路由不存在，但同樣的數字可能由自己的應用、託管平台或反向代理產生；`502` 指向閘道與上游互動的問題；`504` 指向閘道等候上游逾時。要知道由誰發出，可檢查回應標頭、錯誤頁內容、請求識別及對應日誌，不應只看數字便斷言資料庫壞了。[B14][B23]

還有一種容易被忽略的狀況：HTTP 回覆是 200，畫面卻只顯示空白。可能是前端 JavaScript 執行錯誤、重要資源未載入、回應內容格式出乎程式預期、渲染條件不成立，或使用者權限不足但程式沒有清楚呈現。此時在 Network 之外也應檢查 Console 與實際頁面狀態。把一切都當成「網路錯誤」會錯過真正的應用層證據。

有時候同一錯誤在某些訪客身上發生，另一些沒有。可以對照訪客是否有舊 Cookie、不同權限、不同語言、不同資料版本、不同路由與裝置時間；切勿直接推論「平台隨機故障」。對分散式系統而言，**重現條件不同**比「偶爾」這個詞更有資訊量。能夠穩定描述條件，才能設計最小影響的修復。

## 五、假設情境：網站可以瀏覽，下載卻一直失敗

假設一個課程網站提供 ZIP 有聲書資料包，使用者按下載後顯示失敗。首先確認按鈕對應哪條 URL：是否有舊連結、跳轉、憑證授權限制、檔案不存在、伺服器回 403 或 404？如果實際 HTTP 已回 200，還需要知道下載是否真正完成、檔案是否完整，或瀏覽器是否被安全政策與下載目的地限制。瀏覽器的等待逾時也不等於已證實下載失敗；應以實際下載管理狀態、已儲存檔案及檔案完整性檢查為證據。

接著分清**平台網址安全限制**與**站點伺服器錯誤**。例如自動化工具無權打開瀏覽器內部頁面，這可能是工具的受限執行環境，而不是遠端 ZIP 被刪除。反覆叫程式重試讀取同一個受禁止的內部 URL，不會因等待次數增加就變得合法。若平台並未提供下載狀態的可用介面，就應清楚標記「無法驗證最終落盤」，而不是推定成功或失敗。這種保留未知的做法，比虛假完成報告有價值。

若你能在受允許的環境實際取得 ZIP，下一步才是核對大小、解壓、CRC、SHA-256 或內容檔案是否存在。即使某個 HTTP 回應聲稱內容長度符合，也不能單獨證明每個內部檔案都正確。**下載**、**完整性**和**可使用**是三種驗收。這個案例是假設性的故障拆解，沒有對任何個別下載歷史提出新事實。

## 六、修復時要建立對照，而不是一次改五件事

一個可追溯的修復有四步。首先寫下觀察：何種請求在哪些環境失敗。其次提出會導致此現象的假設，例如正式域名指向舊部署。再設計能區分假設的測試，例如比較預覽網址與正式域名的回應標頭和版本識別。最後才修改最小必要設定，並以原本失敗的案例驗證是否恢復。修復後再核對重要相鄰功能，避免同一改動損害其他路徑。

對可能影響多人服務的設定，應有回滾思路。調整前保存原 DNS 記錄、專案綁定、環境變數名稱與部署識別；不要在事故壓力下把所有紀錄清空。若需要變更權限或憑證，先確認真實影響範圍，使用合法管理介面，避免為了方便讓私人資料庫對所有人開放。每一步的證據應包含發生時間，才能知道改動與結果的先後關係。

當排查遇到邊界也要明說。公開 RFC 和平台文件能指引可能的機制，卻無法讀取當下使用者路由器、瀏覽器安全設定或平台內部日誌。沒有觀察到的狀態不能捏造，沒有足夠權限的步驟不能以繞過限制代替。工程的可信度，正是在不確定時仍能保留正確的未知欄位。

## 七、把一次排障變成長期可靠性

每次故障都會暴露系統的可觀測性缺口。若網站只能顯示「失敗」，卻沒有請求識別、時間、錯誤類別與對應日誌，下次就會再次從零猜測。若上傳完成沒有伺服器端確認狀態，使用者會不知道是否該重試；若新版本沒有可辨識的部署識別，管理員無法確認正式域名提供的是哪一版。這些不是華麗的工程功能，而是降低維護成本的基本設計。

本書從網址、DNS、傳輸、HTTPS、HTTP、瀏覽器邊界走到排障，最後留下的是一種判斷方法：每個故障描述都要能回答「目前有哪些可以觀察的事實、哪個推論尚未被證實、下一個最有區分力的檢查是什麼」。這不是保證沒有事故，而是讓你不必在每次事故裡依賴猜測、反覆操作或不具可追溯性的成功宣告。
