# 第五章　測試建立可重複的信心：從單一函式到真實使用流程

開發者在自己的筆電上打開網站，輸入資料並看到「成功」兩個字，很容易認為功能完成。然而，同一個網址在其他瀏覽器可能不同；一般會員帳號可能沒有被測過；上傳檔案若是空檔、超大檔或重複檔，流程可能失敗；同時兩名使用者按下送出時，也可能觸發和單人操作完全不同的結果。測試的目的不是讓報告上的通過數字增加，而是把對系統的信心建立在可反覆執行的證據上。

AI Coding 的特色是程式改得很快，因而測試的重要性反而上升。當生成工具能一天改動幾十個函式，靠人逐頁點選會跟不上變更速度；但若只依賴少數自動測試，仍可能對未涵蓋的地方產生虛假的安全感。良好的測試策略需要同時考慮測試對象、成本、失敗後果，以及哪些觀察必須由真正的使用者完成。

## 一、先知道每一層測試能回答什麼

單元測試通常集中於較小的邏輯單位，例如費用計算、日期轉換或輸入驗證。它執行快速、較容易定位錯誤，卻不代表與資料庫、登入服務或瀏覽器整合後必然正常。整合測試檢查幾個元件合在一起時是否保持契約，例如 API 接到特定請求後是否寫入正確資料，或者資料庫約束是否確實阻止重複紀錄。端到端測試則從較接近使用者的入口檢查整體流程，例如登入、填表、上傳、送出、查看確認頁與取消。

這些分類不是高低貴賤，也不代表所有系統都要按固定比例配置。測試哪一層，取決於可能失敗的位置。若問題是貨幣四捨五入，先測純邏輯比啟動整個瀏覽器有效；若問題是一般會員能不能看到管理員頁，必須跨過身分、路由和資料存取；若問題是按下上傳後 UI 一直不動，就需要在真實瀏覽器檢查等待、事件與網路回應。好的測試組合是用便宜且穩定的方法覆蓋大量邏輯，用較昂貴的端到端測試保護關鍵旅程。

以假設的報名系統為例，總名額規則應接受純邏輯與資料庫層檢查；姓名必填和格式錯誤訊息需要介面測試；送出成功應驗證後端資料確實存在；取消報名則應同時確認使用者介面、資料狀態與重新查詢結果。這比只測一個「報名成功」情境更能指出哪個保證已經成立、哪個仍未知。

## 二、測使用者看見的結果，不要和頁面結構綁死

Playwright 官方最佳實務建議測試使用者可觀察的行為，優先使用角色、名稱、文字或約定的測試識別來定位元素，避免把測試綁死在容易變動的 CSS 結構；它也建議讓各測試彼此隔離，以降低互相污染。[S12] 這背後的道理很簡單：如果把按鈕改成不同顏色或多包一層容器，功能其實沒變，測試不應因為 DOM 位置改變就大量失敗。

例如測試「提交」按鈕時，先找到具有提交語意與可辨名稱的控制項，比指定頁面中第三個 `<div>` 裡的第二個按鈕更穩定。自動化工具不是人，它需要可識別的頁面結構，因此表單標籤、可存取名稱和明確的狀態訊息會同時改善使用者體驗與測試能力。測試友善的介面未必就有好的無障礙品質，但兩者都受益於清晰的語意。

另一個常見錯誤是以固定等待時間解決非同步問題。假如資料有時一秒回來，有時五秒回來，硬寫「等三秒」不是驗證，只是賭運氣。Playwright 的非同步斷言會在設定期限內持續檢查預期條件，適合用來等待頁面出現正確文字或狀態。[S12][S13] 當測試仍失敗，才有資訊指出預期結果遲遲沒有出現。並不是等待越久越好，過長的逾時反而可能拖延真正故障的發現。

## 三、端到端測試首先要控制資料與身份

測試如果依賴正式環境裡「剛好存在」的一筆使用者資料，今天可能成功，明天資料被刪除就失敗。更危險的是測試程式可能直接對正式名單進行修改。Playwright 官方建議隔離測試、控制測試資料，並避免把外部不可控服務當成主要測試對象。[S12] 這不代表所有外部整合都不必測，而是應將可控的應用程式行為與第三方服務的穩定性分別驗證。

假設系統有三類帳號：公開訪客、一般報名者、主辦管理員。端到端測試不應只用主辦管理員完成所有操作。訪客必須不能取得私人名單；報名者只能查看自己的報名；管理員可以依規定審核與匯出。若想驗證「不能看到別人的資料」，必須建立至少兩組彼此不同的資料歸屬，再測試跨身分存取是否被拒絕。只看到一位使用者能查自己的資料，不能推出其他使用者讀不到。

測試資料應容易重新建立與清理，並和真實個資隔離。對開發團隊而言，測試帳號的好處是每次執行都接近同一前提；對顧問而言，這讓驗收不依賴某一個人的手機或電腦設定。如果資料建立本身需要額外流程，就要將建立與清除步驟納入測試設計，而不是長期留下一批無法辨識用途的測試紀錄。

## 四、測試失敗要留下可以重現的線索

當 AI 報告「測試失敗，但重試後成功」，仍需問第一次失敗原因是什麼。可能是測試設計不穩定、非同步等待不足、共用環境有污染，也可能是真正的間歇性服務問題。單純增加重試次數，會讓測試報表變漂亮，卻可能遮蔽使用者偶爾也會遇到的故障。

Playwright 的 Trace Viewer 能回看測試操作、DOM 狀態與網路活動，幫助定位失敗前發生什麼事；官方說明建議在 CI 失敗時使用追蹤資訊調查問題，而不是只憑截圖猜原因。[S13] 追蹤檔也可能包含畫面與請求內容，保存和分享之前應檢查是否含測試帳號憑證或敏感資料。可觀察性越高，越要同時管理資料暴露面。

保留失敗的輸入、環境、版本與時間，通常比一句「好像卡住」更有用。尤其跨瀏覽器或行動裝置問題，應說明系統版本、裝置種類、操作順序與預期結果；沒有重現方法時，先蒐集證據，不應為了消除紅字而隨意修改底層程式。AI 在除錯時可以很快提出假設，但應逐一以日誌、測試或設定核對，而不是把第一個猜測寫成事實。

還有一種錯誤測試很難從一般正向案例發現：測試永遠使用與開發者相同的正常輸入。真實使用者可能貼上空白字元、不同語系的姓名、超長檔名、重複上傳或在手機上中途離開頁面。對這類輸入，測試不必聲稱窮盡所有可能，而是應按後果挑選代表性邊界，例如最大長度前後、有效與失效憑證、原本可接受但會因新版本改變的資料格式。這會讓測試集合更能承受未來變更。

測試也有維護成本。當一項測試長期因與產品目的無關的視覺小改動而失敗，團隊可能開始忽略紅色報告。此時應調整測試的觀察層級，而不是乾脆移除重要驗證。真正有價值的測試會告訴團隊哪一項使用者承諾被破壞；不能解釋其業務意義的測試，則值得重新檢查。

## 五、把測試接到變更流程，才有持續價值

GitHub Actions 官方文件提供對 Node.js 專案在 CI 中安裝依賴、建置及執行測試的流程，並可把執行結果作為工作流程產物保存。[S11] 搭配受保護分支的狀態檢查，能讓至少一部分基本品質條件在合併之前自動執行。[S10] CI 不是單一軟體名稱，而是一種每次變更都重新驗證的工作方式。

門檻需要與風險匹配。所有提交都可以先跑型別與基礎單元測試；重要分支再執行整合與端到端測試；正式發布前則可另外做資料遷移演練、權限反例與人工操作驗收。這種分層並不代表高風險測試可以永遠延後。若本次變更直接涉及資料刪除或支付，對應的整合測試就應成為當次合併門檻。

也不能把測試數量當品質。十項精準的測試可能比一百項只有「畫面存在」的測試更能保護核心規則；反之，只有幾項正向測試也不足以代表真實可靠。可以從主要流程、權限邊界、失敗恢復與曾發生的故障建立測試清單，再逐步擴充。真正的衡量方式，是某種錯誤是否能在傷害正式使用者之前，被可靠地攔下。

良好的 AI Coding 流程應能回答：哪個測試描述這次修改的業務規則？它在什麼環境執行？失敗時留下什麼證據？哪些風險仍需要人工驗收？當這些問題可以被回答，測試就不再是「最後做一下」的儀式，而成為讓快速程式生成不至於失控的工程制度。
