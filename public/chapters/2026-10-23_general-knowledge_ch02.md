# 第二章　連上不等於傳到：IP、TCP 與 QUIC 如何運送資料

在網址已能解析出位址之後，網站仍可能卡在「正在連線」。有人會把這種狀況形容為「電腦明明有網路」，或把速度不佳歸因於「伺服器太慢」。但一個端到端的網頁載入，不只涉及伺服器運算；它還需要封包在網路上被轉送、抵達正確服務、維持連線狀態、處理遺失與壅塞。把這些工作混成單一黑盒子，遇到問題只能反覆重開瀏覽器；把它們拆開，才會明白為什麼同一個網址在不同網路下反應不同。[B07][B08]

## 一、IP 的任務是把封包送往下一站

網路層的 IP 位址可以比喻為可用於路由的目的地標記，但它不是現實世界的門牌，也不保證封包一定抵達。封包從電腦送到家中路由器，再經不同的網路設備與自治網路轉送；每個轉送節點主要依路由資訊決定下一步往哪裡送。路由器並不需要了解使用者是要看活動公告、上傳圖片還是登入帳號。這種分工讓各種應用能共用網路基礎設施。

IP 封包裡承載的通常還有上層協定資料。TCP 與 UDP 是兩種不同的傳輸層安排：它們都有埠號，讓同一台主機可區分不同應用通道。常見的 HTTPS 服務可能使用 TCP 443，也可能透過使用 UDP 的 QUIC 承載 HTTP/3。埠的號碼有慣例，卻不是服務性質的絕對證明。即使連到 443，也不能僅憑埠號推定對方的憑證有效、頁面安全或應用程式正確。[B07][B08][B09]

假設一家公司有兩套服務，一個公開網站、一個內部管理 API。兩者可以在同一台主機上以不同埠開啟，也可以透過反向代理共用對外 443，再按主機名稱與路徑分配後端。若管理 API 不慎直接暴露在公開網路，問題不是「IP 太容易被查到」而是存取控制、網路邊界與應用授權沒有設好。網路通達性與使用權限是兩個層次；封包能送達，並不代表發送者應有權讀寫其中資料。

## 二、為何 TCP 需要先建立連線

TCP 被設計成提供可靠、依序交付的位元組串流。建立連線時，典型流程是三向交握：發起端送出 SYN，接收端回送 SYN 與 ACK，發起端再確認。這不是三封「傳送完整網頁」的訊息，而是在雙方開始資料往來前協調序號與連線狀態。RFC 9293 對這一機制、重傳、流量控制與連線關閉都有規範。[B07]

想像瀏覽器準備送出一個 HTTP 請求：它需要確定對方是否願意接收、雙方追蹤哪一段資料已到達、哪些資料可能重複或遺失。TCP 用序號與確認資訊管理這件事；若發現資料未被確認，實作可能依演算法重傳。這種可靠性不是零成本。若網路延遲很高、封包遺失，重傳與壅塞控制就可能讓使用者等待。尤其一個網站必須先取得 HTML 才知道還要載入哪些資源時，依賴鏈會把延遲放大成明顯的空白畫面。

**延遲**與**吞吐量**容易被混淆。延遲是單次往返或傳遞所需時間；吞吐量是單位時間內能傳多少資料。假設兩條連線都能每秒傳很多資料，但其中一條往返延遲較長，頻繁需要請求與回應的小型互動仍可能較慢。反過來，一個低延遲但可用頻寬小的網路，上傳大型影片也可能漫長。網站性能分析不能只問「網速有多少 Mbps」，還應問等待發生在哪個階段、資源多大、是否需要重複建立連線。

## 三、UDP 與 QUIC 不是「不可靠就比較快」

UDP 本身提供較少的傳輸控制機制，這讓應用有空間自行定義需要的可靠性和時序。QUIC 正是在 UDP 之上建立具有安全、串流、確認、流量控制與壅塞控制等能力的傳輸協定。它不是把「可靠傳輸」整套丟掉來換速度，而是重新安排連線與多路串流的方式。RFC 9000 定義 QUIC 的核心，RFC 9114 則把 HTTP 語意映射到 QUIC 上形成 HTTP/3。[B08][B09]

在傳統以 TCP 承載的 HTTP/2 中，多個應用串流仍會受單條 TCP 位元組串流遺失造成的傳輸層阻塞影響；QUIC 將多個串流的傳遞與重組更獨立地管理，降低某條串流資料遺失對其他串流的干擾。這是架構差異，不是保證 HTTP/3 在任何網路、任何網站、任何瀏覽器下都更快。安全裝置、UDP 阻擋、伺服器支援與網路條件都會影響實際效果。

QUIC 還設計了連線識別碼，讓符合條件的連線在 IP 位址或埠改變時有機會遷移。手機從 Wi-Fi 換到行動網路時，這項能力有實用價值。但它不代表所有應用切換網路都絕不中斷，也不表示對方的網路政策必然允許遷移。規範描述能力與限制，特定產品是否使用、如何回退，需要現場檢驗。[B08] 這是工程判斷常見的陷阱：某協定「可支援」，被誤寫成某網站「一定有」該效果。

## 四、封包送得到，為什麼仍然可能顯示逾時

假設一個網站可以解析，瀏覽器卻不斷顯示連線逾時。可能的路徑包括：網際網路中某段路由不可用；目的地的防火牆未允許對應埠；服務沒有監聽；反向代理把流量交到沒有回應的後端；用戶端代理或企業網路限制了連線。這些都可以產生類似「等不到」的外觀，卻需要完全不同的處理。

`ping` 是常見的網路探測工具，但把「ping 不通」等同「網站離線」或把「ping 通」等同「HTTPS 應用正常」，都不嚴謹。ICMP 的回應可能被網路或主機政策限制；即使取得回應，也只能在某個層次表示路徑與回應存在，不會替 HTTP 請求、TLS 握手或登入功能背書。需要知道 TCP 443 是否可建立連線，可以採用明確測試該目的埠的方式；需要知道網站是否回覆正確內容，則須實際發 HTTP 請求。每一種測試回答不同問題。

若上傳一個大型 ZIP 時，前幾秒很快，後面速度驟降，也不必立刻怪罪瀏覽器。可能是上行頻寬受限、傳輸壅塞控制改變發送速率、伺服器接收慢、代理設備緩衝、應用程式分塊邏輯不當，甚至伺服器已收到資料但花時間驗證。只看畫面上的進度列，無法確定瓶頸在哪裡。除非能觀察網路時序、伺服器處理與最終儲存狀態，否則「上傳慢」仍只是症狀而非診斷。

## 五、假設情境：影片上傳與三種不同的失敗

考慮一個供活動參加者上傳照片或影片的網站。情境 A：使用者打開首頁就逾時，登入畫面完全未出現。此時先確認名稱解析、路徑和連線，而不是調整影像壓縮參數。情境 B：首頁正常，選好檔案後長時間停在上傳 80%。此時至少已證明一部分網路與應用通道能運作，應調查檔案大小、請求是否逾時、代理限額、後端是否等待、是否有可確認的完成回覆。情境 C：顯示 100%，管理後台找不到檔案。這更可能涉及伺服器端寫入、資料庫紀錄、權限或顯示邏輯，而不是把所有過錯推給 TCP。

三個情境都是**假設案例**，不是對任何實際網站的故障結論。它們指出一個深層原則：**資料已離開前端，不等於後端完成持久化；取得「進度 100%」也不等於業務交易成功**。如果網站需要使用者信任，應把伺服器確認儲存完成與可回查的結果作為成功標準，前端進度僅呈現其中的傳輸階段。這也能減少重新整理造成重複上傳的機會。

## 六、效能最佳化必須先辨識真正的等候來源

工程上常說減少往返時間、合併請求、使用持久連線、使用 CDN、壓縮內容。這些方法的效果取決於瓶頸類型。若網站慢在 DNS 解析，改動前端圖片大小未必影響第一次連線前的等待；若慢在大量大圖下載，微調伺服器程式碼也未必有幫助；若慢在跨區域 API 一次次串接，則「每次只是小資料」仍可能形成很長的依賴鏈。測量各階段所花的時間，比記憶一份通用優化清單更重要。

可用一個刻意簡化的估算理解累積效應：假設某條操作流程有五次完全串行的往返，每次網路往返 120 毫秒，不計伺服器計算和排隊，單純往返時間的總下限便是 600 毫秒。若其中一些請求能並行，等待就不一定等於五倍；若必須等待上一步結果，延遲便會累積。這是**假設算例**，不是特定網站實測，也不能拿來推算現實使用者的完整載入時間。

## 七、協定知識的邊界

TCP 與 QUIC 規範說明機制，沒有提供「你的站一定比別站快幾秒」的可移植結論。性能受到運營商、跨境網路、裝置、瀏覽器、CDN、主機、程式架構等共同影響。不同網路可能在不同時間出現完全不同結果。因此，判斷網站「慢」時，要先保留測試時間、裝置、網路和請求，再比較同條件下的改變，而不是只依一次個人感受。

本章最有用的區分是：解析出 IP、封包可到達、傳輸連線成功、加密握手完成、HTTP 有回覆、應用完成業務，代表六個不同層次的命題。它們可能連續發生，但不能相互替代。當你能用哪一層已被觀察證實、哪一層仍是假設的語言描述故障，才真正具備繼續讀 TLS 與 HTTP 的基礎。
