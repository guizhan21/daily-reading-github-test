# 第四章　授權與工具的最後防線：能回答，不等於能讀取或修改

在 AI 應用中，最危險的一種設計不是模型突然變得不聽話，而是模型原本就握有不必要的權力。它可能用一把全域資料庫金鑰查詢所有客戶，也可能透過能寄信、刪檔、修改帳款的工具做事。即使模型始終只回應合理請求，一個權限設定錯誤仍會讓普通使用者接近原本不應取得的資訊。要從「讓 AI 做得到」走向「只讓它做獲准的事」，核心是將身分驗證、授權與動作批准放回確定性的程式邊界。

## 一、先分清「你是誰」與「你能做什麼」

身分驗證回答的是請求來自誰；授權回答的是這個已確認身分能對哪筆資料執行何種操作。兩者不能互換。某位志工登入後，系統知道他是志工，並不代表他可以匯出整個協會所有活動的名單；管理員可以審核作品，也不一定可以刪除系統備份。NIST 的安全與隱私控制目錄把存取控制、身分鑑別、稽核、事件回應等視為需要協同處理的控制家族，不能只在登入畫面做一次檢查就結束。[S14]

對每個敏感操作至少要問四件事：由誰提出、對什麼資源、要做什麼動作、在何種情境下。這些條件可被設計為角色型權限（RBAC）、屬性型權限（ABAC）或其他合適的授權方法。角色適合表達「講師可以查看自己班級」；屬性可補充「只能查看自己所屬活動且尚在審核期間的紀錄」。具體選擇取決於系統規模與權限規則複雜度，而不是採用名詞越新越安全。

在假設的活動報名平台中，可以區分一般報名者、活動志工、主辦窗口與系統管理員。一般報名者能查自己的狀態；志工可能只需看報到所需姓名與部分識別資訊；主辦窗口可處理該活動名單；系統管理員負責系統維護但不必每天閱讀完整個資。這只是設計示例，不代表任何實際組織應照抄。若所有角色共用資料庫最高權限，UI 上就算做了四種不同介面，仍很容易在 API 被直接呼叫時失守。

## 二、物件層級授權決定能否保護真正的紀錄

網站開發常碰到這樣的路徑：「/registrations/123」代表某筆報名資料。若後端只因使用者已登入，就按網址上的編號回傳紀錄，攻擊者換一個數字可能讀到其他人的資料。OWASP API Security Top 10 的「物件層級授權失效」（BOLA）明確討論這種情境：後端需要確認目前身分對指定物件是否具有相應操作權，而不只是使用者能否進入同一個 API。[S10]

這件事和 AI 有特別密切的關係。使用者可能用自然語言說「查詢另外一個人的報名情況」，模型於是生成合法格式的查詢參數。真正的保護不是要求模型拒絕，而是資料 API 只允許查詢請求者可讀的紀錄。就算模型誤解問題、產生錯誤 ID、受到外部文件影響，後端仍應維持相同的權限結論。這稱得上是安全性由架構保證，而非由模型善意維持。

向量搜尋與知識庫也不例外。若檢索服務把不同單位的文件放在同一索引，搜尋分數不具有權限意義。最相似的文件可能恰好最敏感；把文件找得很準，不代表提問者有權讀。OWASP 對向量與嵌入弱點的說明中特別提到跨使用者、跨情境資料外洩及權限隔離風險。安全的檢索服務必須在檢索、取回原文與輸出各階段核對授權，不能只靠提示詞說「不要回答秘密」。[S12]

## 三、最小權限要落實在每一把鑰匙上

最小權限不是讓每個人都無法工作，而是讓人員與服務只持有完成已核准任務所需的能力。假設 AI 只需回答公開課程時間，就不必提供後台金鑰；需要核對報名狀態，也未必需要修改權；必須修改時，可讓特定服務只接受明確欄位、經過確認的對象與受控操作。這比把整份資料庫憑證交給模型，再期待它不亂用更有韌性。[S14][S22]

對接第三方工具尤其要檢查授權範圍。OAuth 權限可能包含「讀取全部郵件」或「代使用者寄信」等不同能力；服務帳號可能因部署方便而擁有整個資料庫的讀寫權。設計時應評估是否可使用更窄的權杖、更少的 API 操作、更短的憑證壽命、分開的測試與正式環境、以及可立即撤銷的存取路徑。這些都是傳統軟體安全原則，AI 只是在工具自動決策時讓問題更容易被忽略。

不能把金鑰直接寫在系統提示詞裡，並認為模型「收到不能說出去的命令」就能保密。OWASP 對系統提示詞外洩的說明指出，提示詞本身可能被誘導重述或概括；機密應留在安全的金鑰管理與伺服器環境，由授權過的後端代表使用者執行具體操作。[S17] 這並不是說每段系統提示詞都會被公開，而是不能把保密與授權的安全性建立在一段可被模型生成過程接觸的文字上。

## 四、人類核准不是萬能，但高衝擊動作需要它

將高風險動作交由人確認，是降低錯誤影響的實用方式。然而「請按確認」也會失效：如果人只看到一個看似正常的標題，卻不知道系統準備寄送哪些資料、修改多少筆紀錄，這只是形式上的批准。有效的核准應顯示動作、目標、範圍、預期影響、是否可以撤銷，並讓核准人有機會拒絕或縮小範圍。

例如 AI 幫主辦方整理尚未聯絡的參加者，然後建議寄送提醒。系統可以先顯示收件者數量、預覽訊息、來源名單、寄件身份與發送時間；確認後才啟動郵件服務。如果查詢名單的權限本來就不足，核准畫面不能代替授權檢查。若某位員工沒有讀取資料的權力，也不應藉由請 AI 寄出而得到全部名單。

核准後還需防止「看到的是一件事，實際執行是另一件事」。在高影響流程中，可以把已審核的參數與實際執行請求綁定，保留識別碼及可檢查紀錄；如果參數在核准後改變，必須重新核准。這是工程設計建議，並非某種系統已具備的功能。其目的在於讓人類的確認真正控制一次具體操作，而不是僅對抽象意圖按下同意。

## 五、模型輸出必須經過業務規則的第二道驗證

假設模型回覆一個結構完整的 JSON，包含「刪除作品編號 81」。JSON 解析成功只證明格式成立，沒有證明作品由提出請求的人上傳，也沒有證明作品不受保存政策限制。後端要分開檢查欄位型別、允許範圍、資源擁有者、角色、操作時點及是否需要雙人核准。OWASP 對不當輸出處理的風險分析強調，不能把生成內容直接當作可信的後端指令或可執行輸入。[S07]

即使系統只生成 HTML 或 SQL，也必須用對應上下文的安全輸出處理與參數化查詢。AI 可能在無惡意的情況下給出不適合直接執行的語句，攻擊者也可能利用它來轉送具有程式效果的文字。此時正確問題不是「這是人寫的還是 AI 寫的」，而是「這份內容會進入哪個解譯器或權限環境」。凡是會產生外部效果的輸出，都需要按下游環境的規則處理。

## 六、稽核應記錄決策證據，而不是蒐集更多秘密

完善的授權與控制應能回溯：哪個使用者在何時提出請求，系統依哪套規則允許或拒絕，呼叫哪個工具、作用於哪些資源、結果是什麼。如果日誌只有「AI 執行成功」，事故發生時很難辨認是否越權。然而把整段對話、全部個資與完整秘密參數寫進永久日誌，又會創造新的敏感資料庫。稽核設計需要在可追溯性與資料最小化之間平衡。[S13][S14]

一個好的稽核紀錄可以保存動作識別碼、使用者身分代號、授權結果、資源分類、時間與失敗代碼，在需要時再由適當權責人調閱受保護的詳細證據。每次部署也要能追溯使用的權限規則版本。若只是存下模型說「我沒有違規」，這不是權限稽核，而是一段未經獨立檢查的自述。

授權也需要版本測試。組織新增一個「協辦窗口」角色時，不只是讓畫面多一個選項，還可能改變哪些文件能被搜尋、哪些工具能被呼叫、哪些資料可匯出。應以不同角色和不同資源的組合測試允許與拒絕結果，並在權限調整後重新執行。若只測管理員的成功操作，最容易遺漏普通使用者不該通過的路徑。

對講師與顧問而言，本章最重要的可教概念是：AI 能提出「我想做什麼」，但系統必須另外判定「誰可以對哪個對象做這件事」。身分驗證、物件授權、最小權限、業務規則、事前核准與稽核共同決定能力的邊界。模型能力不斷更新時，這些原則仍能幫助組織避免把新功能誤當作新的管理權限。
