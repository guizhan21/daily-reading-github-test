# 第二章　讀懂前端、後端與系統邊界：一張畫面為何不等於一個系統

網站架設成功、打開網址能看見介面，常被視為「系統已經完成」。真正投入使用時，問題才浮現：換一支手機登入後資料沒有同步；一位管理員可以看到別人不該看到的紀錄；表單按下送出後一直轉圈；後台查到的是昨日資料。這些現象不一定來自程式寫錯，可能是開發者未分清楚畫面、伺服器、資料庫與外部服務各自擔負什麼責任。

所謂系統邊界，就是釐清某個動作在哪裡發生、由誰授權、會改變哪種資料、失敗後又由誰修復。邊界不是為了把程式切成更多檔案，而是避免把不能信任的輸入當成權限，把暫時畫面狀態當成永久資料，把第三方服務的成功回覆當作整筆業務已經完成。理解這些邊界，是 AI Coding 使用者從「能產生頁面」走向「能判斷架構」的關鍵。

## 一、瀏覽器能做的事，不能代替伺服器應做的事

瀏覽器負責接收使用者操作、顯示頁面、維持部分暫時狀態，以及向後端發出請求。它有滑鼠、觸控、相機、檔案選擇器與本機儲存等便利能力，但也處於使用者能觀察、修改或模擬請求的環境。使用者不一定會經過你設計的按鈕；他可以重送請求、修改請求資料，或者直接呼叫公開的 API。因而任何涉及權限、價格、名額或資料歸屬的關鍵判斷，都不應只存在前端。

使用 Next.js 的 App Router 時，官方文件區分 Server Components 與 Client Components：需要互動狀態、事件處理器或瀏覽器 API 的部分使用用戶端元件；需要從伺服器取得資料的部分，可使用伺服器元件。這是一種組織渲染與程式碼執行環境的方式，並不保證應用程式自然安全。即使某段資料在伺服器元件中取得，回傳到瀏覽器的內容仍會被使用者看見。安全性要看是否只傳遞必要資料，以及後端是否檢查存取權限。[S03]

試想一個租屋管理系統。前端的「刪除租客」按鈕只讓管理員看見，看似完成了權限控制；但若 API 沒有驗證呼叫者角色，任何知道請求格式的人仍可能試著發出刪除。Next.js 官方對 Server Actions 和 Route Handlers 都要求以類似公開 API 的觀點設計授權，建議在資料存取層集中執行敏感操作的權限判斷。[S04] 換句話說，隱藏按鈕是一種介面提示，不能充當系統的防線。

## 二、登入、授權與資料隔離不是同一件事

登入的核心問題是「你是誰」。授權的核心問題是「你能對哪些資源做哪些事」。資料隔離的核心問題是「即使程式有疏漏，某個帳號可讀寫的紀錄是否仍受到限制」。三者可以由不同機制完成，也可能相互補強；把它們簡化成「加個會員登入」容易留下漏洞。

假設兩間管理公司共用同一個雲端資料庫。租客表都有租約、電話與房號。管理員 A 登入後，後端若只用租客編號尋找紀錄，不檢查該筆資料屬於哪一間公司，就可能產生跨租戶存取問題。正確的查詢應同時建立資料所屬單位與操作者權限的關聯；不能依賴瀏覽器傳來的 `company_id` 自稱身份，也不能相信使用者不會嘗試猜測其他編號。

Supabase 的 Row Level Security（RLS）是 PostgreSQL 的資料庫層列級安全控制。官方文件說明政策附著於資料表，會在資料讀寫時執行，並區分 SELECT、INSERT、UPDATE、DELETE 的規則。使用 Supabase Auth 時，可透過 `auth.uid()` 取得請求的登入者識別，作為政策的一部分。[S06] RLS 不自動取代後端的業務判斷，也不代表使用高權限憑證就會依一般使用者政策過濾。它更適合被看成「資料層另有一道可驗證的界線」。

## 三、資料在哪裡保存，決定更換裝置後會發生什麼事

`localStorage` 能方便保存瀏覽器內的偏好與暫時進度，卻不會自動在不同裝置共享，也不能天然提供多使用者共同編輯。使用者清除網站資料、更換瀏覽器或進入無痕模式，都可能失去該處儲存的內容。假設作品牆網站讓家長上傳照片，如果把作品記錄只放在本機，就無法保證在活動現場的大螢幕看到相同內容。這是儲存位置與同步能力的差異，不是「AI 寫不出來」。

資料庫適合保存需要查詢、關聯、共同更新與一定一致性保證的結構化資料；物件儲存適合保存照片、影片或其他大型檔案。兩者之間常以資料庫欄位保存檔案識別或物件路徑。若照片先上傳成功、資料庫後寫入失敗，就會出現孤兒檔案；若先寫資料庫、再上傳檔案失敗，就會有指向不存在物件的紀錄。設計時必須決定如何回復、重新嘗試、定期清理或標記待處理，不能把兩個不同服務的操作誤認為一個自動完成的交易。

還要分清快取與真實資料。快取為了加速回應或降低負載，可能暫時持有舊結果；資料庫的最新值不必然等於每個瀏覽器立刻看到的內容。對公開文章、圖片列表，短時間延遲有時可以接受；對剩餘名額、報名取消、付款狀態，陳舊資料可能導致實際損失。所謂「資料要即時」，應再問允許多大的延遲、誰承擔衝突，以及顯示與真正提交是否採不同規則。

## 四、同步請求與背景工作各有成本

有些功能應在使用者按下按鈕後迅速回覆，有些卻需要較長時間，例如轉換影片、批次產生圖片縮圖、傳送數百則通知、掃描上傳檔案。若把所有長時間工作塞進同一個網頁請求，瀏覽器、網路或執行環境的逾時可能讓使用者只看到錯誤，卻不知道後端已做完多少步驟。把工作排入佇列或背景程序，可讓系統先回覆任務已接受，再在後台逐步執行並記錄狀態；但也引入佇列堆積、重複執行、失敗補償及觀察工具的管理成本。

一個處理上傳圖片的流程可以分為接收檔案、驗證格式、保存原檔、產生縮圖、等待人工審核、公開展示。若審核前不能公開，背景縮圖服務即使完成，也不能自行跳過審核狀態；如果縮圖失敗，原圖是否仍可供管理員審核，也要在業務契約中先決定。這樣拆分的目的不是炫耀分散式架構，而是把失敗限制在可辨識的位置。

不必因為用了 AI 就強制採用微服務。單一 Next.js 服務搭配資料庫與物件儲存，對大量小型應用可能已經足夠。只有當工作負載、部署權限、團隊責任或故障隔離真的需要獨立演進時，才值得增加佇列與專用服務。每多一個邊界，就多一次網路呼叫、一次可失敗的整合，以及需要記錄與檢查的狀態。

## 服務失敗時的責任分界

設計邊界還有一個容易忽略的用處：讓故障能被歸屬到正確元件。假如報名資訊已存入資料庫，但通知信沒有寄出，這不應被描述成「報名失敗」，因為真實的業務結果可能已經成立。畫面可以分別呈現「報名已完成」與「通知寄送中」，伺服器則記錄可重新執行的通知工作。若把兩種結果混成一個成功或失敗，使用者可能因為收不到信而重複報名。

另一類邊界發生在第三方系統。地圖、支付、圖片辨識與寄信服務有自己的權限、費率、容量和故障模式。即使對方 API 平常回應穩定，也要思考對方超時、限流、回傳不完整資料或停止服務時，本地系統如何處理。介面是否保留未完成狀態、使用者能否安全重試、是否有人能人工補處理，往往比多寫幾個漂亮動畫更能說明系統設計品質。

## 五、部署平台不是資料架構的全部

Vercel 官方文件區分 Local、Preview、Production 環境，並允許各環境配置不同的環境變數；Preview 通常用於正式公開前測試，Production 才面向真正使用者。[S14] 不過，預覽網址不代表自動使用測試資料庫。如果預覽與正式環境共用同一組高權限資料庫連線，測試時刪除的可能是正式資料。這類事故的關鍵不是網址不同，而是環境隔離沒有完成。

對於需要存放 API 金鑰、資料庫密碼等秘密的設定，Next.js 官方指出，帶有 `NEXT_PUBLIC_` 前綴的環境變數可被打包到瀏覽器端程式碼，並且在建置時內嵌；因此該前綴應只用於允許公開的值。[S05] 不能因為值放在 `.env` 就把它視為秘密。相反地，伺服器端設定也要看部署環境是否正確提供，以及服務執行時是否會暴露到日誌或回傳資料。GitHub Actions 官方則提供在儲存庫與特定環境保存工作流程祕密值的配置方式，但也提醒避免讓祕密內容出現在執行日誌中。[S18]

讀懂架構的目的，最終是能用白話回答六個問題：使用者操作從哪裡進來？誰驗證身分與權限？真正資料存在哪裡？一個操作會跨越哪些服務？任一環節失敗留下什麼狀態？哪個環境能安全測試而不傷害正式資料？只要這六個問題有答案，就算不親自寫每段程式，也有能力檢查 AI 生成的架構是否適合交付。
